## Common tasks
### Release the lot
1. Read any warnings above the form. They are for information and do not block signing.
2. Enter a [[Reason]], your [[Signing username]] and your [[Signature PIN]].
3. Select [[Sign approved]]. The lot becomes Released and you return to the lot record.
### Find out why you cannot sign
1. If [[Not permitted]] shows, you authored some of the lot's data, or a rule set reserves release for a qualification you do not hold. Select [[Return to the lot]]; another quality person signs.
### Leave without signing
1. Select [[Cancel]]. Nothing is signed.
## Good to know
- You cannot disposition a lot holding your own receipt, supplier certificate, expiry and retest dates, sampling or test data, or a supplier result you proposed, whatever roles you hold.
- The page opens before the lot is ready. Missing evidence, active holds and open investigations are checked when you sign.
- Some rule sets reserve release for people with a Release decisions qualification. Without it, [[Not permitted]] shows and no PIN is asked for.
- The QC disposition card on the lot record lists what would block signing. Any change to the lot after you opened the page makes signing fail; reload and review.
- A supplier result that does not meet the specification, or a discrepancy on receipt, does not block signing. Only an active hold does.

## Purpose

Record the signed QC disposition of a quarantined lot with meaning **approved**, which releases it. This is a QC disposition, not manufacturer release.

## Who can use it

- Sign-in required. **Quality** role only; others receive 403.
- Never a user who authored any of the lot's receipt, supplier certificate, expiry and retest dates, sampling or test data, or who proposed a supplier result in place of a test, even with the quality role (see Independence). Such a user sees the reason, a **Return to the lot** link and no signing form (status 403); no PIN is requested.
- Where a rule set the lot is under reserves its release (policy key `authorization`, `release`), you also need an approved, current qualification Release decisions for the activity it names; every rule set the lot is under asks for its own. Without it you see the reason, **Return to the lot** and no form (403); no PIN is requested. It is checked again under the locks when you sign.
- Requires an enrolled signature PIN.

## Layout

- Breadcrumbs Lots › the lot number › the title. A signing dialog (a plain card without JavaScript), headed with the title: meaning, lot number, the lot record revision shown, the signer, the resulting revision the signature binds (shown + 1), a PIN enrolment link, the form, **Sign approved** and **Cancel**.
- **Qualification notice**: above the form, when a reservation applies and you hold the qualification: "This signature relies on your qualification QUAL-3, for release decisions in “REL-TEST” (Rule set RS-TEST v1), and records it." Information only.
- **Dates notice**: above the form, first, when the lot has expiry or retest dates in force: what the release freezes. Information only.
- **Supplier certificate notice**: above the form, one warning for each supplier certificate of the lot that is not withdrawn and states a result which does not meet the specification (see Rules). It is information only.
- **Supplier result notice**: above the form, one warning for each supplier result that was accepted in place of a laboratory test and still stands (see Rules). It is information only.
- **Contract laboratory notice**: above the form, one warning for each test of the lot whose result was reported by a contract laboratory under an approval that has been revoked since (see Rules). It is information only.
- **Newer versions notice**: above the form, one warning when the versions in force are no longer the ones frozen for the lot (see Rules). It is information only.
- **Replaced requirements notice**: above the form, one line for each signed replacement of the lot's requirements during testing, oldest first (see Rules). It is information only.
- **Scopes notice**: above the form, for a lot whose requirements were assigned under several scopes or with an additional rule set, one line naming the scopes, the specifications and the additional rule sets (see Rules). It is information only.
- **Decided requirements notice**: above the form, one line for each test that the specifications applying to the lot state differently and quality decided for the lot's current requirements (see Rules). It is information only.
- **Decision set aside notice**: above the form, one line for each signed decision of conflicting requirements that was set aside when the lot's requirements were assigned again (see Rules). It is information only.
- For a data author, the same card shows the refusal in place of the form, without the dialog behaviour and without these notices.

## Actions

| Action | Shown when | Who | Result |
|---|---|---|---|
| **Sign approved** | You are not an author of the lot's receipt, supplier certificate, sampling or test data | Quality, independent of the lot's data | Lot becomes Released; "Lot released."; returns to the lot record |
| **Cancel** / Escape | Always | Any | Returns to the lot record; nothing is signed |

## Rules and hidden logic

- **Always checked first**: the lot is still Quarantine ("This lot has already been dispositioned."), has no active hold ("<hold> (<kind> hold) is active: <reason>"), and its rule set is still approved and effective ("An approved, effective rule revision is required."). These apply to both paths below.
- **Opening vs. signing**: the page opens for any quality user whatever the lot's state; the state, hold and evidence checks run only when you sign. The authorship check runs on opening too, so an author is told before entering a PIN.
- **Native path** (the lot has a requirement assignment or native tests; always outside DEBUG). Each failing condition is listed as its own message:
- *Native, requirements*: a current assignment with status Requirements assigned; none assigned or an applicability hold blocks. A hold because the specifications of the lot's scopes state a test differently blocks with its reasons until quality signs which requirement applies (Decide conflicting requirements).
- *Native, additional rule sets*: every additional rule set version frozen with the lot's requirements must still be approved and in force. Otherwise signing is refused with one message for each: "Rule set RS-EU v1, which applies to this lot in addition to its own, is no longer in force. Assign the lot's requirements again, or have quality replace them once testing has started." The lot's own rule set is checked first (see above).
- *Native, samples*: at least one ("The lot requires a sampled and tested record.").
- *Native, sampling provenance*: every sample has a current sampling record under the assigned plan revision; any sampling deviation needs an accepted independent assessment (pending or rejected blocks).
- *Native, analytical evidence*: no open test, none awaiting review, no nonconforming result (unless an investigation invalidated it) and no result against a superseded requirement, no open or confirmed investigation, and a reviewed conforming result for every required test on every sample. A requirement answered by an accepted supplier result is the exception: it needs no test on any sample, and an Open test of it that holds no observation and no raw-data file and is in no QC batch does not block.
- *Native, replaced requirements*: tests are matched to the lot's current requirements by content. A test superseded when the requirements were replaced blocks nothing and answers nothing; its sample needs a test under the current requirement ("Sample S-TEST-001 has no assay test under the lot's current requirements: the earlier test was superseded when they were replaced. Assign the required tests."). Superseded tests are listed with invalidated ones as excluded tests in the frozen evidence.
- *Native, supplier results in place of tests*: a proposal awaiting acceptance blocks ("SRA-1: the supplier's result for assay awaits acceptance by a reviewer."). An acceptance that no longer stands blocks ("SRA-1: the accepted supplier result for assay no longer stands: REASONS. Withdraw it, then propose the supplier's result again or test the requirement in the laboratory."), and its requirement is then unanswered (for example "Sample S-TEST-001 has no assay test assigned."). A proposal that no longer stands, for example because its qualification was revoked before it was accepted, blocks the same way ("SRA-1: the proposal for assay no longer stands: REASONS. Withdraw it, …"). Also "SRA-1: the accepted supplier result for assay does not match the lot's current requirement or is not signed." and "assay has both a laboratory result and an accepted supplier result (SRA-1); withdraw the acceptance."
- *Native, sampling still required*: accepted supplier results do not replace the sample and its sampling record. A lot whose requirements are all answered by supplier results still needs both. This is a design default of this product.
- *Native, no mixed evidence*: foundation manual results on the lot block ("Mixed foundation and native evidence requires reconciliation.").
- *Native, frozen evidence*: on release the assignment ID and hash and the analytical evidence snapshot are stored on the lot. Each accepted supplier result is frozen in it with what it relied on and its acceptance signature.
- **Manual foundation path** (development only: DEBUG and neither assignment nor native tests): at least one sample ("The lot requires a sample and reviewed results."); all required rule-set tests per sample ("Required tests are missing."); every result Reviewed and conforming ("All results must conform and have independent review.").
- **Independence**: "You cannot disposition a lot containing your own receipt, supplier certificate, sampling or test data, expiry and retest dates you recorded, or a supplier result you proposed in place of a test." Authors are users who recorded or corrected the lot's expiry and retest dates, including the recorder of a record that a correction later replaced; recorded or corrected the lot's receipt details, including the recorder of a record that a correction later replaced; recorded, corrected or withdrew a supplier certificate of the lot, including the recorder of a record that was later corrected or withdrawn; proposed a supplier result in place of a test, also when the proposal was withdrawn since; sampled or recorded any sampling record of the lot, including corrected originals and intermediate corrections; recorded observations (including corrected originals), submitted tests, recorded batch QC, opened an investigation, or wrote investigative entries; and, on the manual path, the analysts of the results. Holding several roles never waives this. Writing rules or specifications, assigning requirements or tests, recording or signing a supplier qualification, or signing reviews, supplier result acceptances, assessments and conclusions is not authorship. The check is shown when the page opens and repeated under the lot lock when signing.
- **Contract laboratory notice**: for each test of the lot that is not invalidated, whose current result was reported by a contract laboratory and whose approval has been revoked since, the page shows "T-12 assay was reported by a contract laboratory. The approval this result relied on (CLA-3) was revoked on 2026-11-14 10:30 UTC. The result stands as recorded. The approval's record lists every result that relied on it, for quality to assess under the laboratory's procedure. This does not block the disposition." The result still counts as the test's reviewed result. Place a hold from Holds if the lot must wait for the assessment. Not enforced by this page: the software records no assessment of such a result.
- **Reported results and independence**: whoever recorded or corrected a contract laboratory's report on one of the lot's tests recorded its observations and is an author of the lot's test data. Recording or signing the laboratory's approval is not authorship.
- **Receipt authors**: the receipt check applies on both the native and the manual path. The analyst who received the lot through New material lot recorded its receipt details and so cannot sign its disposition. The check reads the receipt records only: a lot received before receipt details were kept has no receipt author until an analyst records them.
- **Supplier certificate authors**: the check applies on both the native and the manual path. It reads every supplier certificate record of the lot and every withdrawal, so a user stays an author after their record was corrected or withdrawn by someone else. A lot without supplier certificates has no such author. Proposers of supplier results are refused with the same message, on both paths.
- **Dates blockers**: the last checks, on both paths. Each failing one is its own message. A rule set the lot is under (its own, or an additional one frozen with its requirements) requires dates the lot lacks: "Rule set RS-TEST v1 requires an expiry date and a retest date for the lot. Record its dates." (the requirement reads "an expiry date", "a retest date", "an expiry date or a retest date" or "an expiry date and a retest date"). After the expiry date: "The lot expired after 2026-11-01. An expired lot is not released." From the retest date on: "The lot's retest date, 2026-11-01, has been reached. A lot is not released on or after its retest date; correct the dates if its testing supports a later one." The dates are compared with the local date. On the manual path these checks come before the sample check.
- **Release reserved for qualified people (optional policy key `authorization`)**: the refusal reads "Rule set RS-TEST v1 reserves release decisions for people qualified for “REL-TEST”. You hold no approved, current qualification for it.", one sentence for each rule set that asks. The lot's own rule set and the additional ones frozen with its requirements are all asked. Activities match without regard to case. The check is repeated under the locks when signing, on the native and the manual path, after the authorship check. On release the qualification relied on is frozen in the lot's evidence and shown on the lot record as "Released under". A qualification revoked later changes nothing already signed.
- **Dates notice**: "The release freezes the lot's expiry date 2027-05-31, retest date 2026-12-01 (basis: BASIS). Check them against their basis before you sign." It lists only the dates stated, comes before the other notices and never blocks signing. Not shown when the dates were corrected to none.
- **Dates frozen**: the release stores the dates in force with the lot's evidence; the certificate is then checked against them. Recording or correcting dates raises the lot revision, so a page opened before refuses signing.
- **Supplier certificate notice**: for each supplier certificate whose current record is not withdrawn and states a result that does not meet the specification, the page shows "Supplier certificate COA-TEST-001 states a result that does not meet the specification: Assay. Supplier results are not laboratory tests and do not block this disposition." with that certificate's number and the names of those tests. The notice never blocks signing and needs no acknowledgement. A withdrawn certificate raises no notice. The notice uses the comparison stored when the result was recorded.
- **Supplier result notice**: for each supplier result accepted in place of a test that still stands, the page shows "Assay: the supplier's stated result 99.60 % on certificate COA-TEST-001 was accepted in place of a laboratory test (SRA-1, SQ-1)." When the qualification relied on was revoked after the acceptance, the notice continues "The supplier qualification this acceptance relied on (SQ-1) was revoked on 2026-11-14 10:30 UTC. The acceptance stands as signed. The qualification's record lists every result accepted under it, for quality to assess under the laboratory's procedure. This does not block the disposition." The notice never blocks signing and needs no acknowledgement. Place a hold from Holds, or withdraw the acceptance, if the lot must wait. Not enforced by this page: the software records no assessment of such an acceptance.
- **Supplier results and release**: signing does not require a supplier certificate. A stated result that was not accepted in place of a test is not read by the release checks and answers no requirement. A result that does not meet the specification blocks nothing by itself; only an active hold does. An accepted result answers its requirement and is part of the evidence frozen on release. Not enforced by this page: the supplier's qualification is not checked again when you sign. It was checked when the result was proposed and when it was accepted; a revocation since is shown in the notice and does not block.
- **Newer versions notice**: when the lot is in testing and the versions in force for its material, stage and scopes, or of a rule set it is under, are not the ones frozen for it: "The versions in force now are not the ones frozen for this lot: specification SPEC-TEST-001 v2, 1 requirement changed. The lot is dispositioned against its frozen requirements unless quality replaces them first. This does not block the disposition." The list names, whichever apply: the version in force of the lot's own rule set, each specification or additional rule set version in force that differs or newly applies, each one that "no longer applies", "the specifications in force state assay differently, which quality decides with the replacement", and the number of requirements that changed. A revised sampling plan is not listed: the lot keeps the plan its samples were taken under. When the lot's rule set version is the one no longer in force, the notice reads instead "The lot's rule set version is no longer in force: rule set RS-TEST v2 in force now. The disposition is refused until quality replaces the lot's requirements." (signing then fails with "An approved, effective rule revision is required."). When it is an additional rule set version, the notice reads "A rule set version that applies to this lot in addition to its own is no longer in force: rule set RS-EU v2 in force now. The disposition is refused until quality replaces the lot's requirements." (signing then fails with the message under *Native, additional rule sets*).
- **Additional rule set retired before testing**: no notice is shown, because the notices above are worked out only once testing has started. Signing is refused all the same; assign the lot's requirements again.
- **Scopes notice**: for a lot whose current requirements were assigned under several scopes or with an additional rule set: "The lot's requirements were assigned under the scopes general, eu-market: specifications SPEC-TEST-001 v1 (general), SPEC-TEST-EU v1 (eu-market); additional rule sets applied: RULES-TEST-EU v1. A market or customer the lot is for and that is not named here was not applied." ("; additional rule sets applied: …" only when there are any). The scopes are entered when the requirements are assigned; the software does not know which markets or customers a lot is for. The notice never blocks signing.
- **Decided requirements notice**: for each test that the specifications applying to the lot state differently, when the lot's current requirements carry quality's choice (signed on Decide conflicting requirements or with a replacement): "The specifications that apply to this lot state assay differently (limits). Decided on 2026-11-14 10:30 UTC by Quality Test: SPEC-TEST-EU v1 (eu-market) applies, 99 – 101 % · rounded to 2 decimals · method M-TEST-001 v2; not applied: SPEC-TEST-001 v1 (general), 98 – 102 % · rounded to 2 decimals · method M-TEST-001 v2. Reason: REASON". The brackets say what the statements differ in. The person, the time and the reason are those of whoever decided that choice: the signer of the decision, or of the replacement that made it. When the current requirements came from a replacement that carried a choice decided earlier, the notice ends "The choice was carried by the replacement of 2026-11-15 09:00 UTC by Quality Other." The notice never blocks signing and needs no acknowledgement. Signing that decision is not authorship of the lot's data.
- **Decision set aside notice**: for each signed decision of conflicting requirements that was followed by assigning the lot's requirements again (which needs no signature and never applies the decision): "The decision of 2026-11-14 10:30 UTC by Quality Test on the requirements the specifications state differently (assay) was set aside without a signature when the lot's requirements were assigned again on 2026-11-14 11:00 UTC by Quality Other under the scope general." ("under the scopes general, eu-market" for several). Oldest first, whatever the lot's current requirements are. The notice never blocks signing and needs no acknowledgement.
- **Replaced requirements notice**: for each signed replacement, "The lot's requirements were replaced during testing on 2026-11-14 10:30 UTC by Quality Test: REASON Superseded tests, kept in the record and not part of this evidence: T-12 assay.", or ending "Every test carried over." when none was superseded. The notice never blocks signing and needs no acknowledgement.
- **Receipt details are not a release condition**: signing does not require receipt details to exist and does not read the examination on receipt. A recorded discrepancy blocks nothing by itself; only an active hold does. Not enforced by this page: whether the supplier named on the receipt is qualified.
- **Stale page**: any new sample, test change or hold since opening, receipt details recorded later or corrected, a supplier certificate recorded, corrected or withdrawn, and a supplier result proposed, accepted or withdrawn in place of a test, change the lot revision: "Record changed. Reload and review before signing."
- **Identity and PIN**: "Enter your own signing username and PIN." on a mismatch (audited as `signature.identity_denied`); "Enroll a signature PIN first."; "Signature PIN was not accepted."; 5 consecutive failures lock the PIN for 15 minutes ("Signature PIN is temporarily locked."). Failures are recorded (`signature.denied`) even though the disposition is refused.
- **Session**: defaults are a 15-minute idle and 8-hour absolute limit; sessions without recorded login times count as expired. On expiry the next request signs you out with "Your session expired. Sign in again to continue." The inline "Session expired. Sign in again before signing." is an extra safeguard at the moment of signing.
- **Effect**: one transaction sets Released, raises the lot revision by 1, writes `signed.approved` and stores an immutable signature (signer, meaning, server time, bound revision, content hash). A lot is rejected, or cancelled as received in error, through its own signed pages (Reject lot, Cancel lot received in error on the lot record); a released lot has no reversal path in this version.
