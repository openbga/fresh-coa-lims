# Architecture

Product intent is in [product.md](product.md); source and tests define the implementation. OpenBGA QM LIMS uses a conventional Django/PostgreSQL architecture for manufacturing quality control. Versions live in `pyproject.toml`, `uv.lock` and vendored asset notices.

## Shape and boundaries

One Django monolith and PostgreSQL 17 serve one organization/site. Django sessions, forms, ORM, transactions and migrations provide the foundation. Server-rendered Bootstrap pages work without a separate frontend service; HTMX progressively enhances actions. Gunicorn and WhiteNoise serve the container. There is no workflow DSL, repository abstraction, tenant platform, queue or offline synchronization requirement.

| Boundary | Responsibility | Extension rule |
|---|---|---|
| `accounts` | Named users, signed account administration, explicit roles, two-factor sign-in, single sign-on and session revocation | Scientific authority remains separate from account administration |
| `core` | Rule revisions, PIN credentials, signatures, audit, the formula, file import and device format contracts and common transition contracts | Shared module: changes to schema, services and migrations need careful review |
| `suppliers` | The supplier register (who lots are received from) and supplier qualifications | A supplier's identity is immutable; a qualification is a separate signed record for one material and named tests, never a flag on the register, and decides nothing about a lot by itself |
| `quality` | Lot/sample identity, receipt details, expiry and retest dates, the reassessment of released material, supplier certificates, supplier results accepted in place of tests, signed QC disposition, and the signed rejection or cancellation of a lot; DEBUG-only legacy result journey | Native disposition locks the lot and consumes assignment, analytical and hold gates; rejection and cancellation end the quarantine without reading the gates as conditions; receipt details, dates and supplier certificates are append-only, and a supplier's result answers a requirement only through a signed acceptance that still stands |
| `config`, shared templates/static | Routing, environment, application shell and design primitives | Shared module: changes to routing and navigation need careful review |
| `catalog`, `sampling` | Approved method/specification/QC/sampling revisions, method evidence records and lot requirement snapshots | Publish bounded requirements; unsupported applicability must hold |
| `analytical` | Observations/corrections, calculated results, results imported from instrument export files, readings from balances and meters, results reported by contract laboratories, raw-data files, replicates, batches/QC, OOS and controlled retests, for a lot's tests and for the tests of a stability pull | Preserve original data and publish lot blockers/evidence under the lot lock; an accepted supplier result is read through an adapter and is never an observation; a stability pull is reached only through the `ANALYTICAL_STABILITY_PULLS` adapter and a reassessment through `ANALYTICAL_REASSESSMENTS`, and a test of either names no lot |
| `laboratory`, `stability` | Resource eligibility/use, training records, qualification to perform or to review, the data connections of balances and meters, the contract laboratory register and its approvals, protocols/pulls with the acceptance criteria of a pull's tests and its signed outcome, reserves, retention and holds | Publish explicit eligibility and hold/evidence contracts; a contract laboratory's identity is immutable and its approval for a method is a separate signed record; `stability` reads results only through `stability/evidence.py` |
| `impact` | The quality-owned impact assessment of a failure: the tests, lots, stability studies and certificates it names, the decision on each, holds placed through it and its signed conclusion | Reads the records it names and changes none of them; a hold is placed through `stability.services.place_hold` and is the lot's ordinary quality hold; nothing else imports it except the pages that link to it |
| `planning` | Turnaround targets, the plan of each open test (due date, analyst, planned instrument), the work list, the workload, the reminders, and the turnaround and right-first-time figures of reviewed tests | Reads tests, equipment, calibrations, reagent lots and pulls and changes none of them; authorizes no work (the bench still checks the analyst, the instrument and every lot at entry); the dashboard reads its overdue filter |
| `validation` | The laboratory's acceptance of its intended use, freezing the approved configuration and release in force, and its recorded rehearsals of recovery, downtime and upgrades with evidence files; the acceptance journeys command | Reads the approved versions in force from `catalog`, `core`, `sampling` and `stability` and changes none of them; holds no work: what changed since an acceptance is shown, not enforced. The acceptance journeys call only the public services of the other apps, as the pages do |
| `whatsnew` | **What's new**: the changes listed in `changelog.d/`, the generated `CHANGELOG.md` (`manage.py changelog`) and each user's unread count | No models: entries ship with the code and are read from files; a user's last-seen entry is a presentation preference (`core/preferences.py`) |
| `reporting` | Signed CoA issuance/amendments, immutable snapshots, certificate data and stored PDF bytes, for all of a lot's requirements or one scope of the lot; the conformity of each result with every specification of the lot; signed withdrawal of a certificate and the notifications of its recipients; export of a lot's complete record | Consume native evidence and recheck hashes/gates under lock; read a lot's record by model label in one repeatable-read, read-only transaction |

## Integrity contracts

Views and forms handle HTTP, CSRF and field errors. Explicit domain functions authorize transitions and enforce policy. Every mutation must have an actor and meaningful reason where required. Signed transitions lock/recheck the current record revision and relevant authority, then commit the state change, immutable signature and audit event in one database transaction. A stale request must fail rather than sign a different revision. Authorization is checked on the server; hidden buttons and `is_staff` are not release gates.

Rule revisions are separately approved and effective dated. Draft presets are editable seed data; approved historical content is preserved. Approval needs a finite interval. Approving a later version of a rule set, specification, method or sampling plan retires the approved versions whose remaining period it overlaps: `supersession_plan` works out, under the lock that serializes approvals of that kind of document, the moment each stops applying (the later of the new version's start and the signing time, or its own start when it had not begun), refuses a draft that would retire a later-numbered version, and `supersede` writes `superseded_from` and `superseded_by` with an audit event in the signing transaction. The approved content, hash and signature of a retired version are not touched; the guards on approved rows let only those two columns change, and only to be set or brought forward. Every lookup of the version in force (`applies_at`) excludes a version from the moment it is superseded. Decisions retain the exact revision/snapshot evaluated. Selection by material, stage and scope and the resolution of conflicts are explicit (next paragraph); the site is the deployment. Do not merge conflicting obligations by choosing whichever is least restrictive, or any other. Audit and independent review are universal invariants.

A lot is under its own rule set (`Lot.rules`, chosen at receipt) and under every additional rule set whose approved policy carries `applies_to` with `materials`, `stages` or `scopes`; `validate_policy` accepts the key as optional, approval refuses a material or stage that does not exist, and a rule set keeps its kind across versions, so a lot's own rule set never becomes an additional one. `catalog.services.Applicable` takes the scopes a lot is assigned under and its own rule set and reads once what applies: the additional rule set versions in force (`core.services.additional_rules`), the specification of each scope and the method versions. `freeze(decisions)` turns that read into the payload and reads nothing more (`resolve_requirements` is the two together). Lines are compared as testing would freeze them (`same_requirement`): alike, they are one line with its `sources`; different, they are a conflict, returned on `ApplicabilityHold.conflicts` with every statement and what the statements differ in, beside the `blocking` reasons that a decision cannot settle, unless `decisions` names a scope that states the test. One scope without additional rule sets yields `oq.requirements/1` exactly as before, so frozen hashes and the readers of one specification are untouched; anything more yields `oq.requirements/2`, which keeps those keys (`specification` is the first) and adds `scopes`, `specifications`, `additional_rules`, `decisions` and the `sources` of each test. An assignment row keeps its `scopes`. A conflict makes the assignment a hold; `sampling.services.decide_conflicts` is the transition signed on the lot (meaning `requirements_decided`, quality, outside the lot's disposition authors, before testing only). Under the lot lock it reads what applies once, compares the preview token with that read and freezes the same read with the choices, so nothing approved in between is frozen unseen; the token covers every specification, method and additional rule set version read, the sampling plan version, the statements and the requirements stated one way. It refuses a resolution that is still incomplete and adds an assignment with `origin = decided` whose `decision` keeps each choice with who made it, when and why, and the lot revision the signature is bound to. From then on only quality assigns the lot's requirements again (`reassignment_denial`), and a decision set aside that way is a notice at the disposition. Once testing has started the choice travels with `replace_requirements` (`choices`): a choice of the frozen requirements is carried only while the scope that was named still states the test exactly as frozen (`_standing_choices`), and the replacement's evidence keeps the original decider of a carried choice. A conflict that arises during testing therefore never leaves the lot without a move, and a statement revised since is nobody's choice. The gates read the rule set versions a lot is under from its frozen assignment (`sampling.services.applied_rules`): assigning tests and the disposition require each in force, testing through the requirement provider (`require_additional_rules`) because it never imports sampling, and supplier reliance asks every one of them. Reporting adds `scopes`, `specifications`, `additional_rules` and `decisions` to the native evidence only for a lot that has them, so evidence of earlier lots keeps its shape.

A signature stores the individual signer, meaning, server execution time and record revision/content binding. PIN credentials use Django password hashing, never reversible storage. PIN verification is rate limited through persistent failure/lock state; failure events must survive rejection of the scientific transition. Password sign-in, PIN enrollment and own password change share a persistent per-account failure counter: after five consecutive failures (configurable) password authentication is refused for 15 minutes, even with the correct password. Credential fields are masked in error reports. Successful PIN entry is authorization for the immediate checked action, not a reusable approval token. Do not log submitted PINs. HTTP signing re-enters the username and PIN on each signing. Server-enforced idle and absolute lifetimes default to 900 and 28,800 seconds; old sessions lacking login timestamps are rejected. The immutable signature records the authentication channel/components and login time, never raw credentials/session cookies. Trusted in-process services are a separate PIN-only channel, not exposed as a web bypass. Revocation, recovery, identity verification and the deployment procedures still require validation for covered use.

| Authority | Read access | Mutation authority |
|---|---|---|
| Admin | All lab lists/details/history, rule sets, audit filter/export, lot record export and CoA PDF | Account lifecycle only; scientific actions need the designated additional role |
| Analyst | Lab records through each module's shared READ roles | Receipt, sampling and analytical entry subject to eligibility and state checks |
| Reviewer | Lab records through shared READ roles | Independent review within the module's reviewer policy |
| Quality | Lab records, rules and audit | Configuration, disposition and other explicitly authorized quality actions |
| Auditor | Lab records and audit | Audit-review attestation only; no scientific record mutation |
| No recognized role, including a superuser alone | Account access guidance and own credential maintenance | No laboratory or in-app administrative authority |

Account web mutations use the explicit admin role and a fresh username/PIN signature with meaning `account_authorized`. An account revision, whitelisted non-secret before/after audit values and signature commit atomically. Passwords, PINs and their hashes are excluded from evidence. A transaction advisory lock serializes all account administration, including last-active-admin checks across different target rows; row locks and a revision check reject stale edits. Admins cannot grant themselves additional roles or deactivate/remove the last active admin. The sole self-assignment exception is trusted CLI bootstrap: an active roleless superuser can assign exactly admin when no active admin exists. Django staff/superuser flags cannot be changed through the web management pages. The sign-in announcement is a single record shown before authentication; the admin role changes it through the shared signed transition (meaning `announcement_authorized`, revision check, audit of the previous and new text). Its text is escaped before the page-documentation Markdown subset is applied. It is public by design: it must never carry a credential of an account that can change it, and the audit trail retains every version.

Two-factor sign-in (`accounts.two_factor`) uses `django-otp`'s time-based authenticator model and our own `RecoveryCode` rows (SHA-256 digests of 120-bit codes). The sign-in view hands an account with a confirmed authenticator to a second step instead of calling `login()`: the session keeps only the account, its session epoch, the session hash of its password and the start time, and `login()` runs once the code is accepted, so the existing session, throttle and log signals fire unchanged. The second step locks the account and the authenticator rows, rechecks the epoch and password hash, refuses a code during a sign-in lock, and records a failed code with the password throttle in its own transaction. The library's per-device delay is off; its replay protection (`last_t`) is kept. Owner changes confirm the password without resetting the failure count, then the code, and reset only when both pass; for an account with an authenticator, no password-only confirmation resets it. `LoginThrottle.code_failures` counts consecutive wrong codes across locks and stops the second factor at 100 until an administrator reset. The session keeps the account generation read when the credentials were checked, so a factor set up in between still ends it. `ControlledSessionMiddleware` sends an account that `MFA_REQUIRED_ROLES` requires and that has no authenticator to the two-factor page. `signing_context` adds the session's `sign_in_factors` to every web signature. Security keys and passkeys (`accounts.security_keys`, `SecurityKey` rows) use py_webauthn for the Web Authentication checks: each challenge is kept in the session for one ceremony (`sign_in`, `confirm` or `register`) with the relying party ID and origin derived from the request's host (validated by `ALLOWED_HOSTS`) and scheme (`SECURE_PROXY_SSL_HEADER`); an IP-address host offers no keys. A key's answer reaches `two_factor` as a `KeyAssertion` in place of a code and is checked under the same account and row locks, failure counting and stop; the key row keeps the signature count and the digest of the last answered challenge, so a concurrent second use of the same answer is refused even when the count stays 0. `static/js/security-keys.js` reads the options from a `json_script` element and posts the answer in a hidden field, so no inline script is needed. Signing in with a key alone (`login_passkey`, ceremony `passkey`) names no account: the options list no credentials and require user verification, `key_owner` finds the account by the answer's credential ID at the request's relying party, and `complete_passkey_sign_in` locks that account and checks the key under the same rules, requiring the user handle and the UV flag. Each request is started by a POST, so an anonymous visit makes no session. The authenticator admin is unregistered: keys are secrets. Django admin's sign-in page redirects to the application's, so no session starts outside that one sign-in. Single sign-on (`accounts.single_sign_on`) fetches the provider's discovery document itself, once a process under a lock, and gives Authlib's Django client only the checked keys (issuer, HTTPS endpoints, signing algorithms), so the library never loads the document on its own; Authlib then builds the authorization request with PKCE, exchanges the code and parses the ID token (joserfc) with our own claim options: issuer, this client as the only audience, subject, nonce, expiry and issue time, asymmetric algorithms only. The view keeps one pending request in the session (purpose, state, nonce, code verifier, start time and, for a link, the account and its session generation) and pops it when the answer arrives, so each answer is used once and only by the session that started it. A sign-in finds the account by `SingleSignOnLink` (issuer, subject), locks it and hands an account with a second factor to the same second step as a password, with `first` set to `identity_provider`; otherwise it calls `login()` with the configured backend, so the session, throttle and log signals fire unchanged. Linking runs only from the owner's page after `two_factor._reauthenticate`; the page then shows an ordinary link to the provider, so the site's `form-action 'self'` policy is never relaxed. The link is refused when the session generation changed while the person was at the provider.

Every administrative account change advances a session epoch. Middleware rejects older sessions; signing rechecks the locked actor's epoch and forced-password flag to close a mid-request revocation gap. An intentional self-change signs against the locked pre-change actor state and ends that session on success. New web accounts and password resets require password replacement before workspace access. A reset may retain the current password or install a privately shared temporary one; there is no email delivery. The owner's replacement uses current password plus reason, records an unsigned audit event, rotates the session, and preserves only that current session. Existing sessions without an epoch expire when this release is deployed. Trusted operator commands remain audited rather than PIN-signed; their execution environment is an operational privilege boundary.

No user reviews their own authored scientific work, even if they also hold reviewer or administrator roles. Account/privilege changes need attributed audit events. Audit review must identify the records/range reviewed, reviewer, time and outcome; opening the audit page is not itself evidence of review.

Append-only history is enforced with PostgreSQL triggers as well as service boundaries. Database owners can alter triggers: this is protection against ordinary application writes, not cryptographic proof against a database administrator. Use separate migration and runtime credentials in production, least privilege, restricted database access and tested backups. Additive corrections/amendments preserve originals. Retention obligations and disposal blockers are implemented, but no physical/electronic disposal action is enabled.

Scientific values use Decimal/numeric with explicit units, limits and original provenance. Never turn missing or nondetect values into zero. Catalog and sampling revisions are frozen into lot assignments and analytical requirement snapshots. The shared adapter delegates requirement translation to the catalog/sampling contract, then validates the analytical payload without supplying defaults. Native testing accepts numeric, count and qualitative results, limits that include or exclude their boundary, and a declared replicate policy. The requirement payload has four versions: `oq.test-requirement/1` is still emitted unchanged for a numeric line with inclusive limits, so tests already in progress keep their frozen hash; `oq.test-requirement/2` carries every other line shape; `oq.test-requirement/3` has the `/2` keys with a method that states its resource requirements and calculation; and `oq.test-requirement/4` has the same keys with a method that also states its file import (`oq.file-import/1`), whose fields must be the calculation's inputs or the directly entered value. A method with neither keeps its original four keys, byte for byte, inside `/1` and `/2`. A numeric reporting precision rounds the mean half-up; `reporting_decimals=null` preserves exact comparison. Submission rejects nonterminating or more-than-eight-decimal exact means. Individual replicate conformance is checked when configured. A result recorded as less than a value keeps its qualifier and is never used in a mean; a qualitative result stores its outcome and what was observed. Unsupported payloads, and qualitative lines without an approved expected outcome, remain holds, not guessed conversions.

Requirement reassignment is refused under the lot lock once any native test exists. From then on only `sampling.services.replace_requirements` changes a lot's requirements: a transition signed on the lot (meaning `requirements_replaced`) by a quality person outside the lot's disposition authors. It resolves the versions in force for the assignment's material, stage and scopes, the version in force of the lot's rule set and the additional rule sets that apply, keeps the sampling plan, refuses an incomplete resolution without recording a hold, and compares a token of everything the signer was shown with what it finds under the locks. In one transaction it supersedes the tests whose requirement is no longer one of the lot's, adds an assignment with `origin = replaced` that keeps the evidence of the replacement, moves `Lot.rules` to the rule version in force and advances the lot revision with the signature; the lot guard lets the rule set change only to an approved version of the same code while the lot is in quarantine. Sampling never imports testing: the testing side is the adapter `REQUIREMENT_REPLACEMENT_TESTING` (`config.integrations.TestingUnderReplacement`). Testing locks tests before lots, so `sign_transition` takes an optional `prepare` step that runs after the signer is locked and before the signed record is: the replacement locks the lot's tests there, and a test created between the two locks makes it stale instead of being locked out of order. Assigning tests takes the lot's tests before the lot as well, because a repeat is inserted with a link to the superseded test it follows. Assigning tests and the disposition need the lot's rule version in force; the review of a result needs it approved only, so a rule version retired during an investigation strands neither the failing result nor its conclusion.

A test answers a requirement by content (`contracts.content_hash`, the payload without its `source`), so a test carries over when the replaced requirements ask for exactly the same thing. A test in the state `superseded` keeps everything recorded on it, changes only its state and record revision on the way there, is immutable afterwards by trigger, and is skipped by the gate; assigning the lot's tests then adds a linked test of the kind `revised` on the sample of the superseded test. The testing side refuses a replacement while an investigation is open on the lot or while an open test that would be superseded holds current observations. Assignment to a batch requires the test's exact frozen method revision. New batch creation resolves the method version that applies now, and an earlier revision only while open, unbatched tests of lots in quarantine are frozen to it (`earlier_batch_methods`, with the payload frozen on the test): a lot keeps its frozen versions, and a test that cannot be superseded (a retest under an open investigation, a test that holds raw data) must still be able to finish. There is no migration of a test to the current method other than the replacement. A QC batch is fixed by a superseded test only when that test had been submitted, and rejecting a failed batch leaves superseded tests as they are.

A test that cannot be completed is closed by `analytical.services.record_not_completed`, a transition signed on the test (meaning `not_completed`) by the quality role outside the test's data authors. It takes the investigation the test belongs to in `prepare` (investigations are locked before their tests), then the test, then its lot or pull through `_lock_subjects`; only an open test qualifies, and the stale-revision check of `sign_transition` covers every reading, file and batch change, since each advances the test revision. The follow-up is decided by the test, never by the signer: a test with `investigation` set is left to it and advances its revision; current readings outside their limits open an investigation on the test, judged by `outside_limits` as batch and lot rejection judge unsubmitted readings: each reading as recorded and rounded half-up to the reporting precision (`contracts.fails_alone`), and a complete replicate set as `evaluate` would at submission; otherwise a test of the kind `repeat` is created with `parent` set, on the same sample or pull, or on a sample of the lot recorded after the test was assigned (the server time of its `sample.collected` audit event, not the sampling time entered) that holds no original test and whose tests all answer for the same original sample (`repeat_samples`, read under the lot lock), so that one new sample stands in for one sample only and a routine sample recorded before the test is not taken for one; a sample recorded later is the signer's choice, which the signature records. For a test of an investigation the signer must also be someone who could conclude it (`not_completed_authors` mirrors `conclude_refusal`). The page shows, and the record freezes, every corrected reading (`corrections`), since a test that is not submitted is never reviewed. The gate then skips the chosen sample's own requirements, as for a resample, so a routine sample recorded after the test could be chosen; this residual is a signed choice of the signer, not prevented by the software. `reject_batch` locks the investigations of its tests after the batch and before the tests, because a rerun of an authorized retest is inserted with a link to its investigation: without it, a record or a conclusion holding the investigation and a batch rejection holding the test deadlocked. `not_completed_record` (`oq.test-not-completed/1`) freezes the cause, the readings, those outside the limits, the corrections, the raw-data count, the batch, whether anything was ever recorded (`held_work`) and the follow-up. The test guard (migration `analytical.0009`) lets only an open test move to `not_completed`, changing nothing but its state, revision and record, requires the record's schema and cause, and keeps the test immutable afterwards; a check constraint keeps the record present exactly in that state. Such a test is excluded like an invalidated or superseded one: the gate lets its lineage (the repeat, or the investigation) answer for the sample, `lot_evidence` lists it under `excluded_tests` with its cause and signature, the requirement replacement treats it as closed, `results_submitted` and `reject_batch` leave it as it is, and supplier reliance counts it as laboratory work only when it held some. `retests_used` does not count an authorized test closed this way before it held any work, `conclude_refusal` accepts such a test as the original of the investigation it opened, and `conclude` refuses an invalidation while a test of the investigation was closed with a reading outside its limits.

Receiving a lot writes the lot, its receipt details and both audit events in one transaction; the service takes no defaults and refuses incomplete details. Receipt rows are append-only by trigger. A second trigger refuses a receipt row for a lot that is not in quarantine and a correction that points at another lot's record; it reads the lot under a share lock, so it waits for a disposition in progress and then sees the released lot; a partial unique index allows one original per lot and a one-to-one link keeps corrections in a single chain, so the row that nothing corrects is the current one. A correction locks the actor's account and then the lot, requires the record it replaces to be the current one, refuses a correction that changes nothing and advances the lot revision. The supplier a receipt names is an immutable identity row; nothing about a supplier's qualification is read at receipt.

A supplier certificate is a record of the lot, not a test. Recording one locks the actor's account and then the lot, requires a quarantined lot whose current receipt names a supplier, resolves the lot's requirements through the same contract testing uses and refuses a page that was opened before they changed. Each stated result is checked and compared by the frozen requirement's own reading rules and stored with that requirement and its hash; the comparison is never recalculated, and a result whose requirement the lot no longer has is shown as such. Certificate, result and withdrawal rows are append-only by trigger. Insert guards read the lot under a share lock and refuse a row for a lot that is not in quarantine, a correction of another lot's record or of a withdrawn record, and a withdrawal of a record that has been replaced; a record states how many results it holds, the database accepts no more, and a deferred constraint refuses a record that commits with fewer. A one-to-one link keeps each certificate's corrections in a single chain. Testing and reporting never read these rows. The lot gate learns of a supplier's result only through a signed acceptance, described next.

A supplier's result stands in for a test through three records that are signed separately. The rule revision opts in: its policy may carry `supplier_results` with `own_tests`, the tests the laboratory always performs, each of which must be one of the revision's required tests so that a mistyped code is refused instead of leaving the intended test open to reliance; `validate_policy` accepts the key as optional so that revisions approved before it existed stay valid, and a revision without it allows no reliance. A supplier qualification (`suppliers`) names a supplier, a material and test codes with dates; only its state moves (recorded, approved, revoked), by signature, and a trigger freezes everything else. An acceptance (`quality`) names one result row of the lot's current certificate record and the qualification relied on, and freezes what it relied on as evidence: the stated result with its method and limits, the certificate with the people who recorded it, the supplier, the day of receipt, the qualification and the rule revision. Proposing locks the actor's account, then the lot, then the supplier's qualification rows for the material, and refuses a submission whose token differs from the evidence it would freeze, so a proposal never freezes what its author was not shown; signing locks the signer's account, the acceptance, the lot and the qualification it named, rebuilds the evidence and refuses any difference, so a revocation in progress is waited for and a corrected record is never signed unseen. The signer is neither the proposer nor anyone who recorded the certificate's records or the lot's receipt details, whose supplier and date the evidence freezes. Withdrawing locks the account, the acceptance and the lot: a proposal is withdrawn with a reason, an acceptance that was signed through the signed transition, by a reviewer or by quality. Insert and update triggers repeat the essentials for direct writes: a proposal starts as one and carries evidence of the expected shape, belongs to the lot of its certificate, relies on a current record whose result meets the requirement and on an approved qualification that names the test, changes only by being accepted or withdrawn, is accepted only while that record is current and that qualification approved, and changes not at all once the lot has left quarantine. A partial unique index allows one proposal or acceptance per lot and test at a time. Nothing underneath an acceptance is blocked from changing. Instead the acceptance is judged again whenever it is read: when its certificate record was corrected or withdrawn, another current certificate of the lot states a failing result for the test, the receipt names another supplier or another day of receipt than the evidence froze, the lot's requirement hash differs, or the laboratory holds work on the requirement, it no longer stands, answers nothing and blocks the disposition until it is withdrawn. A revoked qualification is not such a reason for an acceptance already signed: it stands and the revocation is shown where the disposition is signed. For a proposal it is, as is a rule revision that is no longer effective, because nobody can sign it any more. Testing reads none of this directly. `ANALYTICAL_SUPPLIER_RESULTS` names the adapter (`config.integrations.AcceptedSupplierResults`); without it no supplier result answers a requirement. The lot gate takes from it the acceptances that are signed and still stand, checks each requirement hash and signature itself, treats those requirements as answered for the whole lot, leaves out the "incomplete" blocker for an untouched open test of such a requirement, and adds the adapter's blockers for proposals and for acceptances that no longer stand. Result entry, reported results, raw-data upload, batch assignment and test assignment ask the adapter which requirements a proposal or an acceptance stands for and refuse work on them, and an acceptance is refused once a test of the requirement holds an observation, a raw-data file, a batch or a decision, so neither can be used to replace the other's outcome. The lot evidence lists accepted supplier results under `supplier_results`, apart from `results` and only when there are any, with the acceptance signature; their proposers and the recorders of the certificate join the evidence's authors, and the certificate of analysis prints them in their own table. A supplier result is never copied into an observation, so replicate, rounding, batch QC and recalculation rules are not applied to it: the comparison recorded with the certificate result, exact and unrounded, is the one relied on.

A lot leaves quarantine once, by one of three signed transitions on the lot: the release (`approved`), the rejection (`rejected`, `quality.rejection.reject_lot`) and the cancellation of a lot received in error (`cancelled`, `cancel_receipt`). The lot guard refuses every change of a lot that left quarantine, lets `disposition_evidence` change only on the way out, and requires a rejected or cancelled lot's evidence to name its `decision` and `schema` (`oq.lot-rejection/1`, `oq.lot-cancellation/1`) and a released lot's never to; a check constraint keeps the state to the four known values. Rejection and cancellation are signed by the quality role outside `disposition_authors` (cancellation also outside the lot's creator). Each page is built from `rejection_preview` or `cancellation_preview`, which read once what the signature freezes (the current assignment, receipt, supplier certificates and results, active holds and, for a rejection, the release gates' messages, every test and investigation); `basis` is the digest of that read, and signing reads it again under the lot lock and refuses a difference. The preview's `reasons` refuse the signature: an open investigation, or an open test holding a current observation that fails its frozen requirement on its own (the comparison `reject_batch` makes), for a rejection; a sample, test, reserve sample, stability study or standing supplier result for a cancellation. The reads take no test locks: every write they depend on locks the lot, so it either commits first and advances the revision or finds the lot closed. Recording batch QC locks only the batch, so whoever records QC on a batch holding an open test of the lot at the moment of signing is not seen as an author; such a test holds no result, and the same person is an author of nothing the rejection freezes. The lot's tests are not changed; testing refuses them through `quarantine_refusal`, and `reject_batch` leaves the tests of a rejected lot as they are instead of refusing the batch. Stability refuses a study on a rejected or cancelled lot and a reserve, obligation or hold on a cancelled one.

A lot's expiry and retest dates are `LotDates` rows (`quality.dates`), append-only by trigger like receipts: an insert guard reads the lot under a share lock and refuses a row for a lot that is not in quarantine or a correction (`replaces`) of another lot's record; a partial unique index allows one original per lot, a one-to-one link keeps one chain, check constraints keep the retest date on or before the expiry date and require a basis with any date (a correction may state none). Recording locks the actor's account and then the lot, compares the record the page showed (`expected`) with the one in force, records `lot.dates_recorded` or `lot.dates_corrected` and advances the lot revision. The recorders join `lot_record_author_ids`, and so the authors refused the disposition, the rejection and the cancellation, the decision between specifications and the replacement of requirements; the certificate evidence adds them to its authors when it carries dates, so none of them issues it. `material_dates` in a rule policy (`expiry`, `retest`, `expiry_or_retest`, `expiry_and_retest`; optional in `validate_policy`) is read from every rule set the lot is under (`sampling.services.applied_rules`). `dates.lot_blockers` ends `disposition_blockers`: a missing required date, the local date after the expiry date, or on or after the retest date. The release stores `dates.frozen` in `disposition_evidence["dates"]`, and a rejection or cancellation in its evidence, only when the record in force states a date, so the evidence of other lots keeps its shape. Reporting reads the record in force by model into the certificate evidence (`dates`, again only when a date is stated), prints it, and `date_blockers` refuses an issue or an amendment after the expiry date, from the retest date on, or when the record in force is not the one a native release froze (the development-only manual path freezes none, so nothing is compared). The lot list annotates the dates in force with subqueries for its columns and Dates filter, comparing with explicit null checks. The lot record export includes the rows.

A released lot is reassessed through `quality.Reassessment` (`quality.reassessment`), the third subject of a test beside a lot and a stability pull. Testing never imports it: `ANALYTICAL_REASSESSMENTS` names `config.integrations.Reassessments`, which answers `requirements`, `refusal` and `lock` as `StabilityPulls` does, and `_lock_subjects` locks lots, then pulls, then reassessments by key and advances the revision of each. A check constraint keeps exactly one of `lot`+`sample`, `pull` and `reassessment` on a test, a partial unique index one original test per reassessment and code, another check the kinds a detached subject takes (original, retest, rerun, repeat: no resample, no revised test), and the subject trigger keeps a linked test with the subject of the test it follows. The requirements are `sampling.services.requirements_in_force`: what the replacement of requirements would freeze for the assignment's material, stage and scopes under the rule versions in force, carrying the lot's standing choices (`_standing_choices`) and refusing any other difference, read only and tagged `reassess` in each source; the moment of the read is left out of its hash so that the page token (`pull_criteria_hash`) changes only with what applies. Starting locks the account and then the lot; an insert guard reads the lot under a share lock and refuses a lot that is not released or whose use a reassessment ended, a partial unique index keeps one open reassessment per lot, and an update guard freezes everything but the decision columns and refuses any change once it is concluded or withdrawn, and a new retest date after the expiry date frozen at start. `analytical.outcomes` holds the judgement of a set of detached tests that the pull's acceptance and the reassessment's conclusion share (`results`, `work_in_progress`, `frozen_rows`). The conclusion is signed on the reassessment (meaning `reassessed`, quality, outside `author_ids`: its starter and the data and investigation authors of its tests); it reads the requirements in force again at signing, so a test the specification added after assignment blocks Suitable until it is assigned, and freezes `oq.reassessment-results/1`; withdrawal (meaning `withdrawn`) is refused while testing is in progress or a result failed. Both lock the lot in `prepare`, after the signer and before the reassessment (the order of starting), because certificate issuance locks the lot and reads its dates: a certificate waits for a conclusion in progress and never issues beside one that ends the use. The insert guard also requires the lot's dates record in force to state a retest date, and the update guard caps a new retest date by that record's expiry date rather than by the basis the row carries. `dates.in_force` reads the expiry date of the record in force and the retest date of the latest suitable reassessment, else of that record, and the reassessment that ended the lot's use; the lot list annotates the same with subqueries (`annotate_in_force`), and the dashboard counts the list's Dates filter. Reporting puts `reassessment` or `use_ended` in the certificate's `dates` only when there is one, adds the reassessment's authors to the certificate's, and refuses a certificate once the use ended; `frozen_at_release` still compares the dates record with the one the release froze. Lot rows are never changed.

An impact assessment (`impact.Assessment`) names its cause (equipment, a reagent or standard lot, a supplier, a contract laboratory, or another one with none) by a foreign key that a check constraint ties to the cause, a period of concern and an optional quality-system reference; its records (`impact.Item`) each name exactly one test, lot, stability study or certificate (check constraint, one partial unique index per kind). `impact.scope` reads, never writes, what the cause finds: resource uses of the equipment or of the reagent lot and its preparations (`reagent_lineage`) in the period, resolved from their recorded contexts (a test, a QC batch's tests, a sample's lot), the studies with pulls stored in a chamber, the lots whose receipt in force names the supplier, the tests a contract laboratory reported; then each test's lot or study, a supplier's lots' studies and the issued certificates of every lot in the assessment, found or added. The start refuses more than 500 records found and adding by hand stops at 500, but finding the records again is never refused, since a record the cause finds must be in the assessment before it is concluded. Every write locks the account, then the assessment, then the record and, placing a hold, the lot (through `stability.services.place_hold`), and advances the assessment's revision, so a conclusion page opened before goes stale. The conclusion is signed on the assessment (meaning `impact_assessed`, quality, outside `author_ids`: the starter, the actors of every `impact.record_added`, `impact.record_decided` and `impact.hold_placed` event of its records, so a decision changed later leaves its first decider out, whoever used the failed equipment or reagent lot or recorded the contract laboratory's reports in the period (`scope.users_of_cause`), and the data and investigation authors of its tests and of every test of its lots); under the lock it reads the records and the cause again, refuses an undecided record or a record the cause finds that is not in it, and freezes `oq.impact-assessment/1` (the records with their state and decision, and each hold's state). Withdrawal (meaning `withdrawn`) is refused while a hold placed through it is active. Triggers keep an assessment's subject immutable, allow only its revision to change while open and nothing once concluded or withdrawn, require the frozen schema on conclusion, refuse deleting records, inserting or changing one while the assessment is not open (read with `FOR SHARE`), changing which record and why, unlinking a hold, and a change that does not advance the record's revision. The assessment reads no other assessment and holds no work by itself: only its holds block anything.

Planning (`planning`) keeps two tables and reads the rest. `Target` rows are append-only by trigger (`planning.0002`); the newest row of a kind of work (lot, stability, reassessment testing, chosen by the test's subject) is in force, and `services.with_due` gives every test, in SQL, the days of the target in force at its `created_at` and the planner's `Plan.due_on` before it, so the work list filters, sorts and pages on the due date and a target change never moves a test already assigned. Changes of the targets serialize on an advisory lock and compare the rows the page showed. `Plan` is one row per test, inserted empty when first planned (`ON CONFLICT DO NOTHING`), locked after the actor's account (`FOR UPDATE OF` the plan rows, in test order), compared with the revision each page showed (0 before the first change), then advanced and audited (`plan.changed`, `plan.taken`) with the due date, analyst and instrument before and after; a selection is planned as a whole or not at all. Test rows are not locked: the plan trigger reads the test's state when the plan is written and refuses an insert or update for a test that is not open or awaiting review, a delete, a move to another test and an update that does not advance the revision. The reminders read the equipment, reagent lot and pull lists' own queries and store nothing. The figures (`planning.figures`) store nothing either: a test belongs to the period of its review signature (`ElectronicSignature` with meaning `reviewed`, found through its indexed audit event), its returns are its `test.returned` audit events, its corrections its observations that supersede another, and its repeats its kind and the tests whose `parent` it is; one SQL query annotates each reviewed test with these and the due date of `with_due`, and the counts, the median and the ninth decile are computed from those rows in exact integer and `Decimal` arithmetic, so every count equals the rows of the list it opens.

Every analytical evidence change locks and advances the quarantined lot revision. Disposition consumes current assignment requirements, analytical blockers and active stability/retention holds under that lock, then captures assignment and analytical evidence in the signed lot. Production cannot fall back to manually entered limits: that path is DEBUG-only without native assignments, and mixed native/foundation evidence is rejected. Independent review includes data authorship beyond the submitting user, including corrected originals and batch QC. Disposition independence also covers whoever recorded or corrected the lot's receipt details, whoever recorded, corrected or withdrew one of its supplier certificates and whoever proposed a supplier's result in place of a test.

A calculation is one approved formula over named inputs. `core.formulas` parses it with a small recursive-descent parser (numbers, input names, `+ - * /`, parentheses) and never passes text to `eval`; arithmetic is exact `Decimal` carried to 50 significant digits and the result is rounded half-up to the approved decimals. The catalog validates a formula before a method version is approved; testing evaluates the formula frozen in the requirement, stores the inputs as entered and the calculation applied on the append-only observation row, and recalculates at submission and at review. A requirement whose calculation is invalid, or whose line is not numeric in the calculated unit, is held.

Recording or correcting an observation or a batch QC result runs behind the configured bench (`ANALYTICAL_BENCH`, the adapter `config.integrations.LaboratoryBench`). Testing never imports the laboratory module. Inside the entry's transaction the bench locks the actor's account first (the same first lock as signing and every laboratory write), then testing takes its record locks, then the laboratory locks the selected equipment, the reagent lineages and the qualification rows, requires a current approved qualification for the method code and checks every selected resource. Success writes one resource-use row per resource and returns the evidence, which is frozen on the observation or QC result and its audit event. A refusal rolls the whole entry back and is then audited in its own transaction. A method version that requires an instrument or a lot refuses an entry that selects none. No configured bench means results are held. The bench checks the fitness of what the analyst selects; it does not decide which instrument or lot a method needs. The resource-use page remains for work outside native testing, and stability chamber use separately checks equipment eligibility. Preserve these boundaries when extending execution controls.

A method's suitability evidence is a catalog record (`MethodEvidence`, its rows `MethodEvidenceCharacteristic`; services in `catalog/evidence.py`) beside the method, not a controlled revision: it is not effective-dated or superseded, and approving a later record retires nothing. A draft's fields and characteristics change under its row lock with an audit event on the record, so independence at approval is read from the record's own audit events (anyone with an unsigned event on it, and its recorder, is refused). The approval signature writes the frozen `content` (every field and characteristic) and its hash; the guard of `catalog.0009` then refuses every change except approved to withdrawn (state, withdrawal time and revision), refuses deletion, and lets characteristics be inserted or deleted only while the record is a draft. A method version points at the record it relies on (`MethodRevision.evidence`); the revision guard of `catalog.0009` lets that column and the suitability basis and reference change on a draft only. Approving the version runs `check_relied_on` inside the signed transition, after the version's lock and the configuration lock, and locks the record (`FOR NO KEY UPDATE`) before reading it, so a withdrawal, which locks the same row, serializes with it; the approved content then carries an `evidence` key (identifier, kind, conclusion, content hash) only when a record is relied on, so versions without one, and every version approved before, keep their content and hashes. Lot requirement payloads are unchanged: they carry the suitability basis and reference as before.

Reviewing or returning a test asks the configured reviewer check (`ANALYTICAL_REVIEWERS`, the adapter `config.integrations.LaboratoryReviewers`) whether the reviewer may act beyond the reviewer role. The adapter reads the approved content of the method version the test froze (catalog); only a version approved with `requires_review_qualification` asks for anything, and approved content never changes, so the answer holds for the test's whole life. The laboratory then requires an approved, current qualification to review that method code (`Qualification.work` `review`; one to perform does not count, nor the reverse at entry). Inside the review's signed transition, after the signer's account and the test and its subjects are locked, the reviewer's qualification rows for the method are locked before they are read, so a revocation, which locks the same row, waits for the review or is seen by it. The qualification relied on is frozen on the test (`review_evidence`), which the review signature binds; the test guard (`analytical.0013`) lets that column change only from awaiting review to reviewed, and a check constraint keeps it empty on any test not reviewed. A return records the same evidence in its audit event. Without the setting testing would ignore the request, so the system check `analytical.E001` refuses such a deployment. A qualification's training records are kept as ids on the qualification (`training`), frozen by the qualification's guard and therefore bound by its approval; training records themselves change only by the trainee's acknowledgement (`laboratory.0006`).

A rule set version's policy may reserve the release of the lots under it and their certificates for qualified people (`authorization`, with `release` and `certificate` each naming an activity; `validate_policy` accepts the key as optional, so earlier versions stay valid). `quality/authority.py` reads what a lot's rule set versions reserve (`sampling.services.applied_rules`: its own and the additional ones frozen with its requirements; a reassessment passes `rules_now`, the versions in force that its requirements in force are read from), one entry per activity, and checks the signer through `laboratory.services.authority_finding`, which requires an approved, current `Qualification` of the matching `work` (`release` or `certify`; no other kind counts). `refusal` is the unlocked preflight that the disposition, certificate and reassessment pages show before any PIN, and that the release, the certificate services and the reassessment conclusion repeat before `verify_pin`. `authorize` runs inside the signed transition, after `sign_transition` has locked the signer's account and the record and the transition has locked the lot (the certificate head, then the lot; the lot in the reassessment's `prepare`): it locks the signer's qualification rows for each activity before reading them, which is the row a revocation locks, so the two serialize without a cycle. The evidence it returns is stored only when something is reserved, so other records keep their shape: `Lot.disposition_evidence["authorization"]` (native releases; the development-only path checks the qualification but stores nothing), `Reassessment.result_evidence["authorization"]` for a suitable conclusion, and `ReportVersion.snapshot["report"]["authorization"]`; each is bound by its signature through the content or snapshot hash. The certificate's data and PDF do not carry it, and `reporting.evidence` never reads it, so evidence hashes are unchanged. Rejection, cancellation, ending the use of material and certificate withdrawal call no check. `authority.relied_on` finds the decisions that relied on a qualification by JSON containment for its record page.

A result reported by a contract laboratory enters through the same bench. Testing records it as the test's observations, every replicate in one transaction, and asks the bench to accept the laboratory's report instead of checking the analyst and the resources: the laboratory module locks that laboratory's approvals for the method, requires one that is approved, not revoked and dated to include the date of the report, writes an append-only use row naming the approval, the test and the report, and returns the evidence, which is frozen on each observation. Signing an approval locks the signer's account and that approval row only, so a report waits for a revocation in progress and is then refused; an insert guard repeats the check in the database. A refusal rolls the entry back and is audited in its own transaction. Such a test needs no QC batch of this laboratory and its values are not recalculated, because the contract laboratory's QC and raw data stay in its report; everything after entry (evaluation against the frozen requirement, independent review, investigations, the lot gates and the certificate) is unchanged, and the lot evidence names the laboratory and its report. A test holds observations made at this bench or reported by a contract laboratory, never both, and a reported result is corrected as a whole: a correction of the same report keeps the frozen evidence, and one that names another laboratory or report asks the bench again. Revocation ends further reliance and does not change results already recorded; the use rows list them for assessment, and the test record, the review page and the disposition page read the approval's current state through the bench to say so. Only this path marks an observation as reported: bench evidence that named a contract laboratory is refused, because the mark is what excuses the batch QC and recalculation of this laboratory.

Raw-data files are rows in PostgreSQL: the bytes as received, their SHA-256, size, declared type and description, attached to a test under the test and lot locks with an audit event, and append-only by trigger. The content is never rendered or executed. A download recomputes the checksum and returns the bytes as an opaque attachment. The only reader is the result import (`analytical/imports.py`), which decodes a stored file as delimited text through `core/file_imports.py` (the standard library `csv` reader, a fixed list of encodings, separators and decimal marks, at most 100,000 rows of 500 columns) with the file import frozen on the test's method version. It never evaluates a cell: a cell is text compared with the test number or the selecting value, or a plain decimal number matched by a strict pattern and converted with `Decimal`. What it reads is stored as text and shown escaped by the templates. An imported observation references its file (`source_file`, a database trigger requires a file of the same test) and keeps the row and cells read (`source`); submission and review read the file again and compare. A middleware ahead of the CSRF check refuses an upload that declares more than `RAW_DATA_MAX_BYTES` plus 1 MiB with status 413 before its body is read, an upload handler stops a file above `RAW_DATA_MAX_BYTES` while it is being received, and the upload form checks the size in the browser first. A test holds at most 20 files, so the limit also bounds database growth and backup size. Larger instrument data sets and automated imports still need a deliberate storage design; Render's ephemeral filesystem is not that store.

Readings from balances and meters cross three boundaries. `laboratory.DeviceConnection` says how an instrument answers: its format (`core/device_formats.py`), serial settings and the serial number it reports; it is append-only by trigger (`laboratory.0005`), one per equipment is current (a partial unique constraint), and setting or ending one locks the equipment row first. The browser (`static/js/device-readings.js`, the Web Serial API) sends the format's requests and passes the device's bytes on, base64-encoded, to `analytical:instrument_read`; it never sends a value. `analytical/readings.py` takes the account lock through the bench, then the test and its subjects, reads the connection through the bench bridge (`LaboratoryBench.connection`, locking that row, so ending it waits), reads the bytes with the format's strict parser (plain printable ASCII, the exact lines of the format, a stable status, a plain decimal converted with `Decimal`, the serial number and the unit compared with the connection and the value) and stores `analytical.InstrumentReading` with the text as received, the connection's evidence as it stood and the server time, audited `instrument.read`. A replicate names readings by id: under the entry's transaction, after the bench has locked the selected equipment, `claim` locks the readings and requires the test, the value, the reader, an unused reading, the instrument among the selected equipment, its connection still current (`LaboratoryBench.current_connections`) and the value text equal to the reading's; the observation is then saved and the readings linked. A trigger (`analytical.0012`) refuses deleting a reading and any change except linking it once to an observation of the same test recorded by the reader; a partial unique constraint keeps one reading per value of an observation. Submission and review parse every linked reading again and compare it with the observation (`reading_problems`). Nothing is parsed in the browser, and nothing the browser sends is rendered unescaped.

Stability protocols generate scheduled pulls and retain acceptance, reserve and retention evidence. Released lot rows and their scientific evidence remain immutable: do not reopen a released lot to fit a pull into the quarantine testing workflow. A pull is tested in the system instead. An `AnalyticalTest` belongs to a lot (`lot` and `sample`), to a stability pull (`pull` alone) or to a reassessment (below); a check constraint keeps exactly one, an insert trigger keeps a rerun or retest with the subject of the test it follows, and another keeps an investigation's `lot` equal to its test's (empty for a pull). Because a pull's test names no lot, every reader of a lot's tests, investigations and samples (the lot gate, its evidence, disposition authorship, certificates) is unchanged and cannot count it. Testing never imports `stability`: the setting `ANALYTICAL_STABILITY_PULLS` names `config.integrations.StabilityPulls`, which answers `requirements(pull)` (the acceptance criteria of the protocol's specification in force, translated by the catalog contract and frozen on each test), `refusal(pull)` and `lock(pull_ids)`. Every transition on existing tests locks their subjects through `_lock_subjects`: the lots by key, then the pulls and their studies by key, refusing a lot out of quarantine and a pull that is not pulled or whose study is closed, and advances the revision of what it locked; assigning a pull's tests locks the pull through the same adapter after the account and the pull's tests, reads the criteria again under that lock and refuses a token that differs from the criteria the page showed. Accepting a pull is signed on the pull: under the pull lock it reads `stability.evidence.pull_results` once, checks it, sets the outcome and freezes `stability.pull-results/1` from that same read on the pull, which the signature content binds; a reviewer who authored any of the pull's test data or investigations is refused. Closing a study and recording a pulled pull as missed lock the pull or study and refuse while testing is in progress (a test awaiting review, an open test holding results or raw data, an open investigation; a place in a QC batch is not work, and batch rejection leaves an open test of a closed pull as it is); a pulled pull is also not missed while it is ready for acceptance or holds a failing result, so a failure is recorded only through the signed acceptance; testing locks a test before its pull, so such work either commits first and refuses them, or is refused after them. A draft protocol can be withdrawn (state only, guarded by trigger) so that a draft that can never be approved does not block its code. A pull is tested here or linked to other evidence, never both. Retention obligations preserve their anchors and calculation basis; missing anchors or active holds block disposal eligibility.

Native reports resolve the exact assignment ID, lot and payload hash captured by signed disposition, verify the payload digest, and take specification and method evidence only from that frozen assignment. Missing or unverifiable evidence holds issuance; live requirement collectors cannot replace it. Holds remain live until signing, including holds placed after lot release. Issuance rechecks the reviewed evidence hash and authority under lock; a stale preview requires renewed review, without a separate persistent draft-snapshot workflow. WeasyPrint renders only the frozen snapshot; it loads only the vendored certificate font and status glyphs, by exact URL, and refuses every other fetch. Snapshot, version, issued PDF bytes/checksum and amendment linkage are stored in PostgreSQL in the signing transaction; a rendering failure rolls back issuance. Downloads verify and return stored bytes rather than regenerating from current records. An amendment adds a version and retains the original. A withdrawal is signed on the certificate head (meaning `withdrawn`, quality, no independence rule: it protects the recipient) and is final: the head guard (migration `reporting.0003`) lets the withdrawal columns be set only on the move from issued to withdrawn, in one revision step that leaves the version count and hashes alone, and refuses any later change, so the versions and their PDF bytes stay readable as issued and no amendment follows. A partial unique constraint keeps one current certificate per lot and recipient, so a later issue to the same recipient opens a new numbered certificate. Recipient notifications are append-only rows that do not advance the head's signed revision; their insert guard reads the certificate with `FOR SHARE` and accepts a row only for a withdrawn one.

For a lot whose frozen requirements name more than one specification, the native evidence carries `conformity` (`reporting/conformity.py`): each reportable result of the frozen analytical evidence and each accepted supplier result, judged against the statement of its test in every specification version of the payload. The approved content of each version is read by its id and used only when it digests to the `approved_hash` frozen in the payload; the method version is the one frozen for the lot's test (all specifications were read at the same instant). A statement the lot applied is judged by the test's own frozen requirement (or, for a supplier's result, by the comparison recorded with it); any other is translated through the catalog contract (`test_requirement`) and parsed by the analytical one (`parse_requirement`), then `Requirement.evaluate` runs on the test's current readings, or `Requirement.conforms` on the supplier's stated reading. A different unit or result type, another outcome pair or criterion text for an outcome, and, for the laboratory's results, another replicate count, method code or a retest allowance lower than `retests_used` of the result's investigation are reported as not judged with their reason, never converted; readings are read once for all the tests. Evidence of a lot under one specification keeps its shape. `Report.scope` names the scope a certificate is for ("" for all of the lot's requirements); it is set when the head is opened, and `reporting.0004` replaces the head guard so that it changes only on a draft head that was never issued (left when signing failed after the head was opened), by itself and with an audited `report.scope_changed`; once a version is issued it is identity like the other columns. `conformity.scope_view` derives from the evidence alone what a certificate for a scope prints (its specifications, the results of the tests they state with that statement, their methods and the investigations of those tests), and `scope_blockers` refuses issue and amendment, under the lock with the other blockers, when a result fails or cannot be judged against it or a test it requires has no result. The evidence hash does not depend on the scope; the snapshot keeps it under `report.scope`, and the certificate partial renders the scope's view from the snapshot, so the PDF and the screen agree.

Inside the signing transaction, after the snapshot, `reporting/certificate_data.py` builds the certificate data (`oq.certificate-data/1`, [certificate-data.md](certificate-data.md)) from that snapshot alone: it reads each printed field by name, through `conformity.scope_view` for a scope certificate, so the bytes do not depend on the key order PostgreSQL gives the stored JSON, carry no internal ids beyond the identifiers the certificate prints, and give moments in UTC to the second; on a scope certificate a statement's `applied` flag is left out. The renderer writes the PDF as `pdf/a-3a` (tagged, sRGB output intent, embedded fonts) with the data as an associated file (`AFRelationship /Data`), and adds the PDF/UA-1 identification and its PDF/A extension schema to the single XMP RDF that WeasyPrint writes; the certificate partial takes its heading levels from `certificate_headings` (h1 and h2 in the PDF, under the page title on screen) because a tagged document starts at H1. `ReportVersion` stores `data`, `data_sha256` and `pdf_format` in the same row as the PDF; the version guard of `reporting.0002` already refuses any update, and a check constraint keeps all three present or all three absent. Versions issued earlier keep null data. Building the data inside the signing transaction, like rendering, rolls the issue back when it fails. Downloading the data verifies its checksum and records `report.data_downloaded`. The lot record export writes each version's data as its own file and checks it.

A certificate check (`reporting/checks.py`) finds an issued version by `pdf_sha256` or `data_sha256` (both indexed, `reporting.0006`), never by number or id, and never loads the stored bytes. The check views replace the request's upload handlers with `HashingUploadHandler` before anything reads the body, so they are `csrf_exempt` and check the token in an inner `csrf_protect` view (Django's documented pattern); the handler hashes each chunk, keeps none of it and stops past `RAW_DATA_MAX_BYTES`, under the unread refusal of `UploadSizeMiddleware`. The answer is read in a transaction that locks the certificate head (`FOR NO KEY UPDATE`), which an amendment or a withdrawal holds while it is signed, and is kept as an append-only `CertificateCheck` whose insert trigger rereads the head under a share lock and refuses any other answer or an unknown version; a check that finds nothing writes nothing, and a check without an account adds no row when one of the same version and answer is already kept that day (read under the same lock), which bounds what one file can add to the certificate and its lot's exported record. The signed-in view requires a reading role in the service. The view without an account (`public_check`, `/check/`) answers 404 unless `CERTIFICATE_CHECK` is set, uses no session, messages or redirect, refuses a cross-site POST (`Sec-Fetch-Site: cross-site`, or an `Origin` other than its own or a trusted one) with 403, takes a slot of the one-row `CheckWindow` (`bulk_create(ignore_conflicts=True)` then a row lock, the time read after it, so an emptied table recreates it and a request that waited does not restart the window) before the body is read and answers 429 with `Retry-After` past `CERTIFICATE_CHECK_RATE` a minute, and sends `Cache-Control: no-store` and `X-Robots-Tag: noindex`. The limit is per deployment rather than per client because the client's address behind a proxy is not trusted; a checksum of 256 bits cannot be guessed, so the limit bounds load, not discovery. Its template renders the shared answer partial without the recipient or links into the staff pages; a signed-in reader who uses it is named on the check.

## Integration gate

Before merging a change that touches shared contracts or infrastructure, run Ruff, PostgreSQL pytest, Django checks, migration drift checks and collectstatic. Contract tests prioritize denied/self-review actions, effective rules, stale revisions, PIN failure/lockout, atomic rollback, immutability and failed/incomplete disposition. Run a native headless synthetic journey through approved specifications, sampling, batch QC, independent review, disposition and PDF issuance/amendment with distinct actors. Exercise OOS/retest and unsupported-requirement holds, and inspect keyboard access, error behavior and PDF output. The DEBUG-only `seed_demo --journey` remains a smaller foundation demonstration; it is not evidence of native journey acceptance. Every product requirement is traced to its tests in `docs/traceability.toml`, and CI builds the [validation pack](operations.md#validation-pack-of-a-release) of each commit from that map, both suites' results and the [acceptance journeys](operations.md#acceptance-journeys) run with the application image. The journeys (`validation/acceptance.py`) commit their records through the public services, because `verify_pin` refuses to run inside an enclosing transaction so that failed attempts persist; the command therefore runs only in the database `--database` names, which must hold no account and be migrated to exactly the release. A direct database change it attempts to show a guard is undone in its own transaction whether or not the guard refuses it, and only the guard triggers' SQLSTATE (`P0001`) counts as a refusal. Passing development tests is not regulated-system validation.
