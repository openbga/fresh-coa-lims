# Changelog

All notable changes to OpenBGA QM LIMS (named OpenBGA Fresh CoA LIMS until 2026-11-16) are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The project is pre-1.0 and does not yet promise a stable interface.

## [Unreleased]

### Added

- Validation records of the laboratory, under the new sidebar item **Validation** (app `validation`). **Intended use** (`validation:use_list`, `use_new`, `use_detail`, `use_accept`, `use_withdraw`): quality records what the system is used for and what is outside it, the supported assays (methods with an approved version in force), the process owner and the system owner, other responsibilities, the validation report and the known issues and conditions; a different quality person accepts it with a signature that freezes every approved rule set, specification, method, sampling plan and stability protocol version in force and the running release (`SOURCE_REVISION` or `RENDER_GIT_COMMIT`), and supersedes the previous acceptance. The list and the accepted record show what changed since. **Rehearsals** (`validation:rehearsal_list`, `rehearsal_new`, `rehearsal_detail`, `rehearsal_file_new`, `rehearsal_file`, `rehearsal_accept`, `rehearsal_withdraw`): quality or admin records a rehearsal of recovery from backup, downtime and reconciliation, or an upgrade, the recorder attaches its evidence files, and a quality person who did not record it accepts it. Guidance in `docs/operations.md` ("Validation records of the laboratory").
- Single sign-on with the organization's identity provider (OpenID Connect authorization code flow with PKCE), off unless `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` are set; also `OIDC_PROVIDER_NAME`, `OIDC_SCOPES`, `OIDC_TOKEN_AUTH_METHOD` and `OIDC_PROMPT` (default `login`). Owners link their own account on the new page **Organization sign-in** (`accounts:single_sign_on`); the sign-in page offers **Sign in with** the provider's name (`login_sso`, `login_sso_callback`). Administrators remove a link with the signed account action `remove_single_sign_on`; **Force password reset** (`reset_password`) and two-factor resets (the account action and the `reset_two_factor` command) now also remove the account's link.

### Changed

- New tables `validation.UseAcceptance`, `validation.Rehearsal` and `validation.RehearsalFile` (migrations `validation.0001_initial` and `validation.0002_guards`, whose triggers keep recorded content immutable, allow only the signed or withdrawn transitions and keep evidence files append-only). New audit actions `use_acceptance.recorded`, `use_acceptance.superseded`, `use_acceptance.withdrawn`, `rehearsal.recorded`, `rehearsal.file_attached` and `rehearsal.withdrawn`; the acceptances are `signed.accepted`. The restore check's `raw data files` check also verifies rehearsal evidence files, and its summary counts both. `RAW_DATA_TOTAL_MAX_BYTES` is one ceiling for raw-data files and rehearsal evidence together, for both kinds of upload (`core.uploads.stored_bytes`); the refusal now reads "This deployment has reached its storage limit for files."
- Renamed the product to **OpenBGA QM LIMS** and the repository to `openbga/qm-lims` (the former `openbga/fresh-coa-lims` address redirects): application name, titles, top bar, footer, certificate and record PDFs, passkey and authenticator-app names, README, documentation, presentation and project links. The presentation moves to <https://openbga.github.io/qm-lims/> (the old address no longer serves it). The Python package is `openbga-qm-lims`, backup file names in the runbook start with `qm-lims-`, and the CI image tag is `qm-lims:ci`. Unchanged on purpose: the database name and user `open_qual`, the Render resources `fresh-coa-lims`, `fresh-coa-lims-db` and `fresh-coa-lims-demo-reset` and the demo at `fresh-coa-lims.onrender.com`, the backup manifest and restore report format identifiers (`fresh-coa-lims.backup-manifest/1`, `fresh-coa-lims.restore-check/1`, so existing backups still verify) and the `freshcoa-pagedocs-*` browser storage keys. Issued PDFs keep their original bytes.
- `sign_in_factors` can be `["identity_provider"]` or `["identity_provider", <second factor>]`. Account audit values gain `single_sign_on` (the linked issuer, subject and label, or null); new audit actions `account.single_sign_on_linked`, `account.single_sign_on_unlinked` and `account.remove_single_sign_on`. New table `accounts.SingleSignOnLink` (migration `accounts.0009_single_sign_on_link`). The sign-in log gains `signin.single_sign_on_failed`. New dependencies `authlib` (with `joserfc`) and `requests` (with `urllib3`, `idna`, `charset-normalizer` and `certifi`).
- Expanded the roadmap and product delivery notes with planned lot rejection and reassessment, cross-record impact assessment and certificate withdrawal, intended-use acceptance evidence, sample handling, continuing analytical assurance, periodic review and archive/retirement assurance. No features are implemented by this documentation update; no data import or export scope is added.
- Signing in with a key alone: `sign_in_factors` can be `["passkey"]`. The new setting `PASSKEY_SIGN_IN` (default `true`) offers it; set it to `false` to ask every account for its password first. `accounts.security_keys.verify_assertion` takes the purpose `passkey`, for which the ceremony names no account, and then requires the user handle and user verification. When a key cannot be used, the message of `static/js/security-keys.js` ends with the form's `data-security-key-fallback` (default "use a code"). The sign-in log gains `signin.passkey_failed`.
- Security keys and passkeys: `sign_in_factors` can be `["password", "security_key"]`; account audit values gain `authenticator_app` and `security_keys` (a count). New table `accounts.SecurityKey` (migration `accounts.0008_security_keys`): public key, credential ID, signature count, host name (`rp_id`) and the owner's name for each key; no secret. New dependency `webauthn` (py_webauthn), which installs `cryptography`, `pyOpenSSL`, `cbor2`, `pyasn1` and `pyasn1-modules`. Two-factor sign-in's start buttons are now **Set up with a security key or passkey** and **Set up with an authenticator app**; for an account without an app the second step's field is labelled **Recovery code**.
- The `authentication_context` of a web signature gains `sign_in_factors`: `["password"]`, `["password", "totp"]` or `["password", "recovery_code"]`, as the signer's session signed in. Account audit values (`before`/`after` of `account.*` events) gain `two_factor`, `two_factor_stopped` and `recovery_codes_left`. `LoginThrottle` gains `code_failures`.
- New dependencies: `django-otp` (time-based codes and the authenticator model, apps `django_otp` and `django_otp.plugins.otp_totp`) and `segno` (the QR code). The library's per-device delay is off (`OTP_TOTP_THROTTLE_FACTOR = 0`): failed codes count toward the account's own sign-in lock instead. Its admin page for authenticators is not registered.
- Django admin's own sign-in page (`/admin/login/`) no longer signs anyone in: it redirects to the application's sign-in, with the admin page to return to, so the sign-in lock and the two-factor step apply to every session.
- `accounts.authentication.confirm_password` takes `reset=False` to leave the failure count alone after a correct password, for a check that continues with a second factor; for an account with two-factor sign-in it never resets the count, so changing the password or the PIN cannot clear failures between guessed codes.
- A test belongs to a lot or to a stability pull. `AnalyticalTest.lot` and `.sample`, and `Investigation.lot`, are empty for a test of a pull, which has `pull` instead; a deployment that reads tests or investigations must accept both. Testing asks the class named by the new setting `ANALYTICAL_STABILITY_PULLS` (`requirements`, `refusal`, `lock`) about pulls; without it no pull is tested in the system.
- A stability pull with its own tests takes no linked sample or external evidence, and the pull page shows **Link evidence** only while it has none. Accepting a pull also refuses whoever produced data for, or investigated, one of its tests.
- Long structured values in the history of a record page are named instead of printed in full; the audit trail keeps them.
- **Assign requirements** takes **Scopes** (one or more, separated by commas) where it took one **Scope**. `sampling.services.assign_requirements` accepts `scopes` as well as `scope`, and `catalog.services.resolve_requirements` accepts `scopes` and `decisions`.
- A lot assigned under several scopes, or under an additional rule set, freezes a requirement payload with the schema `oq.requirements/2`: the keys of `oq.requirements/1` (`specification` is the first specification) and `scopes`, `specifications`, `additional_rules`, `decisions` and, on each test, the `sources` that state it. A lot under one scope and its own rule set keeps `oq.requirements/1` unchanged. A deployment that reads the payload must accept both.
- A rule set whose policy states `applies_to` is not offered when a lot is received and is refused by `receive_lot`. A rule set cannot gain or lose `applies_to` from one version to the next.
- Assigning tests and the disposition require every rule set version the lot is under to be in force, the additional ones included, and a supplier's result is relied on only when each of them allows it. A requirement provider named by `ANALYTICAL_REQUIREMENT_PROVIDER` may offer `require_additional_rules(lot)`; a provider without it applies no additional rule set.
- The rule set approval page counts, for a version being retired, the quarantined lots whose requirements apply it as an additional rule set as well as the lots received under it.
- The database constraint `lot_assignment_replacement` is replaced by `lot_assignment_origin`, and `sampling_lotassignment` gains the columns `scopes` and `decision`.
- The specification form and page no longer say that overlays are never applied together: a lot is assigned under every scope it falls under.
- The native evidence of a certificate lists `scopes`, `specifications`, `additional_rules` and `decisions` for a lot that has them; evidence of a lot under one specification keeps its shape.
- The evidence of a replacement (`oq.requirement-replacement/1`) gains `versions` (every specification and additional rule set version that changed), and `decisions` with `signed_at` when a choice between differing statements is part of it. Earlier rows are unchanged and are read as before.
- After a refused signature the replacement page carries the token and the lot revision of what it then shows, so it can be signed after review without being opened again; before, every further attempt was refused as stale.
- Assigning a lot's requirements locks the account before the lot, like every other change to a lot.

- Approving a version of a rule set, specification, method or sampling plan whose effective period overlaps an approved version is no longer refused with "Effective dates overlap an approved version." The earlier version is retired instead: it stops applying from the new version's start, or from the moment of approval if that start has passed, and keeps its approved content and signature. The approval page lists what the signature retires. A draft that would retire a later-numbered approved version is refused.
- A lot on a rule version that has been retired cannot have tests assigned or be dispositioned until its requirements are assigned again (before testing) or replaced (during testing) under the version in force. Assigning requirements before testing now moves the lot to the version in force of its own rule set.
- Reviewing a result no longer requires the lot's rule version to be in force, only approved, so a result awaiting review and an open investigation are not stranded when a later rule version is approved. Assigning tests and the disposition still require it.
- The new-lot form offers only the rule versions in force.
- **New QC batch** also offers an earlier revision of a method while open tests not yet in a batch are frozen to it; before, such tests could not get a batch once their method revision was no longer in force. `create_batch` takes an optional `revision`.
- Assigning a lot's requirements again after it was sampled keeps the sampling plan version its samples were taken under. Before, a plan version approved in between left the earlier samples blocking the lot with no way to clear them.
- Assigning tests locks the analyst's account first, like every other change to a lot; one account that signed while it assigned tests could meet a database deadlock and an error page.
- Once testing has started, assigning a lot's requirements again is refused with "Testing has started on this lot, so its requirements cannot be assigned again. Quality can replace them with a signature."
- The testing gate matches a test to a requirement by what the requirement asks for, not by the document that states it, so a test carries over when a lot's requirements are replaced by identical ones.
- Tests have a new state, Superseded, and a new kind, Repeat under replaced requirements. A deployment that reads test states or kinds must handle both.
- `core.services.sign_transition` takes an optional `prepare` step that runs after the signer is locked and before the signed record is.
- Replacing a lot's requirements during testing asks the class named by the new setting `REQUIREMENT_REPLACEMENT_TESTING` (`effects`, `lock`, `apply`) what happens to the lot's tests. Without the setting requirements cannot be replaced once testing has started.

- A rule set policy may carry the optional key `supplier_results` with `own_tests`, the list of test codes the laboratory always performs itself. A rule set without it allows no reliance on supplier results; rule sets approved earlier stay valid unchanged.
- The testing gate asks the class named by the new setting `ANALYTICAL_SUPPLIER_RESULTS` (`lot`, `standing`, `standing_by_lot`) which supplier results were accepted in place of tests. A deployment that replaced the testing adapters must provide it; without the setting no supplier result answers a requirement.
- A supplier certificate result can now count towards QC disposition, but only through a signed acceptance. The lot record, the supplier certificate page and the supplier register say so where they used to say that supplier results never count. The supplier page no longer shows "Not recorded in this register" under Qualification; it lists the supplier's qualifications.
- Whoever proposed a supplier's result in place of a test cannot sign that lot's QC disposition. The refusal now reads "You cannot disposition a lot containing your own receipt, supplier certificate, sampling or test data, or a supplier result you proposed in place of a test."
- A test whose requirement a supplier's result is proposed or accepted for shows "Not tested · supplier result" and takes no observation, reported result, raw-data file or QC batch until that is withdrawn; no test is assigned for such a requirement.
- A bench class named by `ANALYTICAL_BENCH` now also answers for contract laboratories (`contract_choices`, `authorize_contract`, `record_contract_refusal`, `contract_notice`). A deployment that replaced the bench must add them.
- A test that holds a result reported by a contract laboratory can be submitted and reviewed without a QC batch, and its replicates are corrected together from **Correct contract laboratory result**.
- Whoever recorded, corrected or withdrew a supplier certificate of a lot cannot sign that lot's QC disposition.
- Whoever recorded or corrected a lot's receipt details can no longer sign that lot's QC disposition. The **Number** field of the new-lot form is now **Lot number**.
- `ANALYTICAL_BENCH` replaces `ANALYTICAL_ELIGIBILITY_CHECK`. A deployment that overrides the old setting must name a bench class instead; without one, results are held.
- Adopted the OpenBGA Fresh CoA LIMS name and certificate-and-leaf mark across the application, presentation and newly issued certificates.
- Moved the source repository and presentation to the `fresh-coa-lims` slug, with the hosted demo at `fresh-coa-lims.onrender.com`.
- The Render Blueprint and hosted demo now deploy `develop` automatically once CI checks pass; controlled deployments keep automatic deployment off.

### Fixed

- Text typed into a signing form before the page had finished loading no longer continues in the PIN field: the dialog script now leaves the focus in the field being typed in. The stability browser journey had failed on this once in CI.
- The warning that a copy of a security key may exist is logged only for an answer the key signed: the signature count is now compared after the signature is checked, so an unsigned answer can no longer raise it.
- Confirming a new authenticator app after 100 wrong codes stopped two-factor sign-in no longer clears the stop; a setup started before the stop is refused, and only an administrator's reset clears it.
- Recording sampling now locks the analyst's account before the lot, the order every other change to a lot uses. An analyst who recorded sampling and another record of the same lot at the same moment could meet a database deadlock and an error page; nothing wrong was saved.

### Added

- Validation pack of each release. `docs/traceability.toml` traces every product requirement of `docs/product.md` to the tests that give evidence for it, and `tests/test_validation_pack.py` refuses a requirement without a test, an entry that does not exist or a test that is not traced. `scripts/validation_pack.py` (`check`, `environment`, `build`) builds the pack: `index.html`, `requirements.csv`, `traceability.csv`, `pack.json`, each suite's JUnit results and environment, the requirements, regulatory matrix and map of the commit, the release notes and `SHA256SUMS`. Each suite's conftest writes the commit the tests run on into the JUnit file, and `[skips]` in the map names the tests that may be skipped, with the reason. CI's application and browser jobs write their JUnit results, and a new `validation-pack` job builds the pack after both and the container smoke job pass and keeps it as the artifact `validation-pack-<commit>` for 90 days. The pack is supplier evidence for a laboratory's own validation, not a validation of the system.
- Signing in with a security key or passkey alone, without the password. **Sign in** offers **Sign in with a passkey** (when the site is opened by its host name), which opens `/accounts/login/passkey/`: **Use your passkey** asks the browser for a key the person added on **Two-factor sign-in**, with no account named, and the key must check its holder's PIN, fingerprint or face. The key's credential identifies the account and the answer must carry its user handle. Refused answers are logged and not counted (a signature cannot be guessed, and counting would let anyone who has seen a credential ID lock the account); an account that is locked or stopped refuses even a valid key. A request is answered once within five minutes. A key that does not check its holder still works after the password. The PIN is still re-entered for every signature.
- Security keys and passkeys (Web Authentication) as a second sign-in factor. On **Two-factor sign-in** an owner adds a named key (**Add a security key or passkey**, page `/accounts/two-factor/security-key/`) after confirming the password, and a second factor once two-factor sign-in is on; the first key turns it on and shows ten recovery codes. The second sign-in step offers **Use your security key** beside the code field, and every owner change can be confirmed with a key by leaving the code empty. A refused key counts like a wrong code toward the sign-in lock and the 100-failure stop; each challenge is answered once; a signature count that does not increase is refused and logged. Keys can be removed one by one (the last one turns two-factor sign-in off, refused for a required role), and **Remove the authenticator app** keeps the keys. The administrator reset removes keys too. Keys work only at the host name they were registered at, over HTTPS or on `localhost`. New audit actions `account.security_key_added`, `account.security_key_removed`, `account.authenticator_added` and `account.authenticator_removed`.
- Two-factor sign-in. **Two-factor sign-in** (`/accounts/two-factor/`, linked from Account access) sets up an authenticator app: confirm the password, scan the QR code or type the key, and confirm with a code from the app; ten one-time recovery codes are then shown once. An account with an authenticator signs in in two steps: the password, then a current code or an unused recovery code on `/accounts/login/verify/` within five minutes (`MFA_PENDING_SECONDS`). Each code from the app works once; wrong codes count toward the account's sign-in failure limit and lock (`LOGIN_FAILURE_LIMIT`, `LOGIN_LOCK_SECONDS`), and 100 consecutive wrong codes stop the second factor until an administrator resets it. New recovery codes, a new app or turning it off need the password and a current code. The new setting `MFA_REQUIRED_ROLES` (comma-separated laboratory roles or `all`; empty by default) requires it: such an account reaches only the two-factor page, password change, page help and sign-out until it is set up. Shared demonstration accounts cannot set it up and are never required to.
- **Reset two-factor sign-in** on an account (admin, signed with the meaning `account_authorized`, not on one's own account) removes its authenticator and recovery codes and ends its sessions; the audited command `reset_two_factor <username> --actor <administrator> --reason ...` does the same from the operator shell. **Users and roles** shows and filters accounts by two-factor sign-in.
- New audit actions: `account.two_factor_enabled`, `account.two_factor_replaced`, `account.two_factor_disabled`, `account.two_factor_stopped`, `account.recovery_codes_replaced`, `account.recovery_code_used` and `account.reset_two_factor`. The sign-in log adds `signin.second_factor_requested` and `signin.second_factor_failed`.
- Stability testing in the system: a stability protocol names the specification that states its acceptance criteria, and its approval is refused while that specification's version in force cannot answer a test of the protocol. **Assign tests** on a recorded pull creates the tests of its time point, each freezing the criterion in force; they are recorded, reviewed, batched and investigated like release tests and belong to the pull, so the record of the study's lot, released or not, does not change. A failing result opens an investigation that holds the pull; a retest of the material pulled can be authorized, a resample cannot. **Accept pull** records whether the reviewed results meet the acceptance criteria and freezes them with the signature; a confirmed failure is accepted with the outcome that they were not met. The study page shows the results of each storage condition by time point beside the criteria, and the stability overview counts pulls outside the acceptance criteria. **Assign tests** refuses criteria approved after the page was opened. A study is not closed while testing of its pulls is in progress.
- **Withdraw draft** on a draft stability protocol: its author or a quality person withdraws a draft that will not be approved, with a reason, and the next version of the code can then be drafted. Protocols have a new state, Withdrawn.
- **Mark missed** also applies to a pull that was taken but cannot be tested, when nothing of its testing is in progress, it is not ready for acceptance and none of its results failed. Rejecting a QC batch leaves an open test of a missed pull, or of a closed study, as it is.
- Backup and restore checks. `python manage.py backup_manifest --output FILE [--dump ARCHIVE]` reads the database in one read-only snapshot and writes a manifest: each table's row count and SHA-256 fingerprint, the columns, constraints, indexes, triggers and functions, the applied migrations and the sequence positions, and checks of the stored evidence (signature hashes and their audit events, issued certificate and raw-data checksums, enabled triggers). With `--dump` it runs `pg_dump` from the same snapshot and records the archive's checksum. `python manage.py verify_restore --manifest FILE --report FILE [--archive ARCHIVE]` checks a restored copy against the manifest and writes a report to keep as evidence; it fails unless the copy equals the manifest and its evidence is intact, and refuses the source database as a copy. Both commands only read, never overwrite a file and write files readable by their owner only.
- The application image includes the PostgreSQL 17 client tools (`pg_dump`, `pg_restore`, `psql`), and the container smoke job backs up, restores and checks a seeded copy with the image.
- Export of a lot's complete record: **Export record** on the lot page (admin, quality and auditor, the roles that read the audit trail) downloads one ZIP file with a printed copy (`record.pdf`), an electronic copy (`record.json`, schema `oq.lot-record/1`, every stored field with its label, kind and choices), the lot's raw-data files and issued certificates byte for byte, `manifest.json` and a `SHA256SUMS` list. Everything is read in one repeatable-read, read-only transaction. It covers the lot's receipt details, supplier certificates and accepted supplier results, requirement assignments, samples and sampling records, tests and the tests of its stability pulls, observations, raw-data files, investigations, QC batches, certificates, stability studies, reserves, retention obligations and holds, the instruments, reagent lots and contract laboratory reports used, the configuration they name (including the specification, method and rule set versions frozen in its requirements), every signature with its manifestation, the audit trail and its reviews. The checksums of stored files and the hashes stored with signatures, certificates, requirement assignments and approved versions are recomputed and each outcome is stated. The export states its purpose and is recorded in the lot's audit trail (`lot.record_exported`) with the package's SHA-256; nothing else changes.
- Several sets of requirements on one lot: a lot's requirements are assigned under one or more scopes (`general` and named market or customer overlays), and the approved specification of each scope applies in full. A rule set whose policy carries the optional key `applies_to` (`materials`, `stages`, `scopes`) applies to every lot it names beside the lot's own rule set. A test the specifications state alike counts once. A named scope with nothing configured, or a rule set that requires a test no applicable specification requires, places the lot on an applicability hold.
- A signed decision where the specifications that apply to a lot state a test differently: nothing is merged and neither statement is picked. A quality person who authored none of the lot's data chooses which requirement applies, gives a reason and signs (meaning `requirements_decided`, page **Decide conflicting requirements**); the statements not chosen stay in the record, on the disposition page and on the certificate. During testing the same choice is part of the signed replacement of the lot's requirements.
- Controlled replacement of a lot's requirements during testing: when a specification, a method or the rule set has been revised, a quality person who authored none of the lot's data reviews what the versions in force would change and signs the replacement with a reason. Tests whose requirement is exactly the same carry over. The others are kept as recorded, marked superseded and never counted; assigning the lot's tests again adds a linked repeat under the new requirement. The earlier requirements stay in the record, the sampling plan is kept, and the lot moves to the version in force of its rule set. A replacement is refused while an investigation is open on the lot or while a test that would be superseded holds results or raw-data files that were not submitted. Migrations `core.0006`, `catalog.0006`, `sampling.0004`, `analytical.0007` and `quality.0011` add the columns and replace the database guards; they change no existing row.
- Reliance on a supplier's results: quality records a supplier qualification for one supplier, one material and named tests, with how the supplier's results were confirmed, an evidence reference and validity dates; a second quality person signs it and quality can revoke it. Where the lot's rule set allows it, an analyst proposes a result stated on the lot's current supplier certificate in place of the laboratory's test and a reviewer who neither proposed it nor recorded the certificate or the receipt details signs the acceptance. The proposal is refused unless a signed qualification covers the supplier, the material, the test and the day the lot was received, the certificate states the method and the limits, the stated result meets the specification, no other certificate of the lot contradicts it and the laboratory has not started testing the requirement (a result, a raw-data file, a QC batch or a decision); a refusal by the rule set or for want of a qualification is audited. An accepted result answers its requirement for the whole lot, is listed apart from the laboratory's own results where the disposition is signed and on the certificate of analysis, and can be withdrawn while the lot is in quarantine: a proposal with a reason, a signed acceptance with a signature. An acceptance stops standing, and blocks the disposition, when the certificate record, the receipt's supplier or date, or the requirement it relied on changes. No preset allows reliance, and the software does not decide which tests are identity tests or how often a supplier is confirmed again.
- Results from contract laboratories: quality keeps a register of contract laboratories and, for each method a laboratory may perform, an approval with an evidence reference and validity dates that a second quality person signs and that can be revoked. An analyst records what the laboratory's report states for a test (the laboratory, the report number and date, where the report is kept and every replicate). The entry is refused unless an approval covers the date of the report, and the approval relied on is kept with the result. The result then follows the usual path: independent review, investigation of a failing result, QC disposition and the certificate of analysis, which names the laboratory and its report. The laboratory's and the approval's pages list the results that relied on them.
- Supplier certificates: for a quarantined lot received from a supplier, an analyst records what the supplier's certificate of analysis states (its number, issuer, date and printed lot number, where it is kept, and for each of the lot's approved requirements the result, method and limits as stated). Each result is compared with the lot's requirement and shown as meeting it or not. These are the supplier's results: they answer no requirement, are not part of the disposition evidence and are not printed on the certificate of analysis. A result that does not meet the specification is shown on the lot record and on the disposition page and does not hold the lot. A correction adds a linked record; a record made in error is withdrawn and kept.
- Receipt details and a supplier register: a lot is received together with where it came from (a supplier from the register, or made on site), the supplier's and manufacturer's lot numbers, the delivery document, the date, the quantity, the containers and what the examination on receipt found. Details are never edited; a correction adds a linked record with its reason while the lot is in quarantine. Quality keeps the register, which records identity only and does not qualify a supplier. The lot list shows the supplier and searches supplier and manufacturer lot numbers. Lots received earlier have no receipt details until an analyst records them.
- Calculated results: a method version can define one formula over named inputs with units, approved and frozen with the version. The analyst enters the inputs, the system calculates the value, and the result keeps the inputs, the formula and the method version. Submission and review calculate again.
- Equipment and reagent checks at result entry: recording or correcting a result or a batch QC check names the instruments and the reagent or standard lots used. An entry is refused when an instrument is out of service or out of calibration, a lot is not released or expired, or the analyst has no current qualification for the method, which now applies to batch QC as well. A method version can require an instrument, a lot or both. After a failed calibration the equipment page lists the tests and QC batches that used the equipment.
- Raw-data files: a file can be attached to a test, is stored with its SHA-256 checksum, never changes and is returned unchanged on download. `RAW_DATA_MAX_BYTES` sets the largest accepted file and `RAW_DATA_TOTAL_MAX_BYTES` an optional ceiling for all files together. A larger file is refused in the browser before it is sent, and the server answers an oversized upload with status 413 without reading it.
- More result types in native testing: counts, qualitative results (conforms or does not conform, absent or present) recorded with what was observed, results reported as less than a value kept as recorded, and specification limits that exclude their boundary. Certificates show the acceptance text and the result as recorded. A qualitative specification line now needs an expected outcome; lines approved without one are held until a new version states it.
- Sign-in announcement: one notice on the sign-in page that administrators write, publish and withdraw with a signed, audited change. The development seed can publish its non-administrator demo accounts there (`seed_demo --publish-accounts`).

- Approved methods and specifications, sampling plans and sampling assignments, with independently approved revisions and frozen applicability snapshots on lot assignments.
- Lot and sample records, numeric observations with replicates, and method QC batches.
- Out-of-specification investigations with controlled assessment, retest and resample authorization, and conclusion.
- Independent signed review and QC disposition that checks assigned requirements, review state, investigations, independence and active holds.
- Immutable PDF certificates of analysis with signed issuance, amendments, stored bytes, snapshots and checksums.
- Laboratory resource records and method-specific analyst qualification authorization.
- Stability protocols and scheduled pulls, reserves, retention obligations and holds.
- Shared rule revisions, PIN signatures (hashed, rate-limited, re-entered for every signing) and attributed audit history.
- Named user accounts with explicit roles, signed account administration, session limits and a read-only Django admin.
- In-app page documentation for every staff page, and a static presentation website published with GitHub Pages.
- Sign-in throttling, a same-origin Content-Security-Policy and credential masking in error reports.
- Container image, CI workflow, a Docker Compose profile for local evaluation and a Render Blueprint for manual deployment.

### Limits

- Greater-than results and batch QC checks other than directly entered numeric values with inclusive limits are not supported. A method states that an instrument or a lot is required, not which one.
- Stability testing compares each result with its acceptance criterion. Trend rules, a significant change from the initial value, shelf-life evaluation, a hold on the lot after a failing result and reports to authorities are left to the laboratory.
- Manufacturer batch release is a separate decision and is not performed by the software.
- Multi-factor authentication, identity proofing, PIN recovery policy, backup schedules and storage, restore acceptance, retention and intended-use validation remain the responsibility of each deployment.
- Segment presets are synthetic drafts, not complete policies.
- No regulatory compliance, validation or certification is claimed. Use synthetic data only.
